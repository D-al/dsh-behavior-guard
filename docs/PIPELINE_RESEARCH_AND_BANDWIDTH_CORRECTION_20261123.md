# 流水线调研结论 + 带宽/搬移代价第一性原理修正（2026-11-23 晚）

> 用户两问：① 试改 scheduler 开流水线但保持 MoE cache 优势 ② 如何逼近带宽上界？搬专家还是搬数据代价最小？能否压缩后给 CPU 算？

## 一、流水线：调研后决定**不实施**（诚实结论）

两路独立源码分析一致，我认同：

### 1.1 删 `llama-context.cpp:581` 那行不够
- pipeline 有 5 个前置条件（`:574-581`）：`n_devices()>1`、`n_gpu_layers>n_layer_all`、`split_mode==LAYER`、`offload_kqv`、`!has_tensor_overrides()`、`moe_cache_size==0`
- **生产两处独立不满足**：① 单 GPU → `n_devices()==1`（CPU 是 backend 不是 model device）；② 我们用 `--cpu-moe` → `has_tensor_overrides()` 为真
- 所以 pipeline 不是"被 MoE cache 单独挡住"，而是**本来就不适用于我们的单 GPU + CPU offload 场景**

### 1.2 即使强开，decode 阶段也无效
- `llama-context.cpp:1831-1833`：graph reuse 时强制 `ggml_backend_sched_synchronize`——多轮 decode 复用图时 pipeline 自动失效
- 真正能重叠的只有"图内 split 重叠"（`ggml_backend.cpp:2155 prefetch_inputs`），它**不依赖 pipeline 且已经开启**，源码 `:2178-2182` 还特意为 copy callback 让路

### 1.3 copy callback 与多 copy 硬冲突
- `llama-moe-cache.cpp:858` 注释自曝单 copy 假设；`:805-806` 的 `ggml_backend_synchronize(backend)` 是全 backend 同步，会把 4 个 copy 串行化
- 去掉同步则会静默读到被覆盖的 slot_map（**输出错误而非崩溃**，最难发现的那类 bug）

### 1.4 收益/风险
- 理论上限 0-20%，实际大概率 0-10%；而本机 sd≈4 t/s，收益可能测不出来
- 风险：静默输出错误、cache 命中率下降、GGUF 兼容性
- **决定：不实施。** 这是"调研后决定不做"而非"失败"

## 二、带宽上界：我之前"带宽墙"的判断需要修正

### 2.1 重算：MoE cache 命中后 DDR 流量很小
| cache 命中率 | miss 专家/token | DDR 读 | 34 t/s 时带宽 | 利用率(35-40GB/s) |
|---:|---:|---:|---:|---:|
| 0%（全 miss）| 320 | 550 MiB | 18.3 GB/s | 50% |
| 50% | 160 | 275 MiB | 9.1 GB/s | 23% |
| **70%** | 96 | 165 MiB | **5.5 GB/s** | **14%** |
| 85% | 48 | 83 MiB | 2.7 GB/s | 7% |

**如果 cache 命中率真是 70-85%，DDR 带宽只用了 7-14%，根本不是带宽墙。**（注：cache 命中率是估算，之前尝试用优雅退出拿 `llama_moe_cache:` 命中率日志但拿不到——`log_stats()` 只在析构打印，`terminate()` 强杀不触发。这是待补的证据。）

### 2.2 真正的瓶颈：专家串行导致的延迟暴露
源码铁证（`ggml-cpu.c:1730-1785`）：
- 外层 `cur_a` **逐专家串行**，内层 8 线程只切分单个专家的 n_ff 输出行
- decode 时 `nr1=cne1=1`（每专家 1 token）→ `nchunk1=1`、`nchunk0=nth=8`
- 即：**8 个专家＝8 个串行 gemv 阶段**，每个阶段 8 线程协作
- 后果：每个专家的 1.72MB 权重读取是"冷启动"式随机访问，DDR 延迟无法被后续专家重叠 → CPU 线程在等内存，590% 占用但 ALU 只 7-10%

**这才是"带宽没打满但 CPU 满载"的解释：latency-bound，不是 bandwidth-bound。**

## 三、搬专家 vs 搬数据：代价对比（回答用户第二问）

| 方案 | 搬什么 | 每次量 | 代价 | 实测 |
|---|---|---|---|---|
| **搬数据到 CPU**（当前 share=1.0）| 激活（F32→Q8_K）| 2048×4B ≈ **8 KB** | 近零，权重本就在 DDR | ✅ 最优 |
| 搬专家到 GPU（share=0）| 专家权重 | **1.72 MB × miss 数** | PCIe 远慢于 DDR，8G 装不下 | ❌ 慢 28% |

**当前 share=1.0 已是代价最小的方案**——把极小的激活搬到 CPU，让巨大的权重原地不动。

## 四、压缩后给 CPU 算？

- **权重**：已是 q4_K（4.375 bpw），再降（Q3/Q2）质量风险大且收益不确定（见 Q3_K 调研）
- **激活**：ggml 已做 F32→Q8_K 转换（`ggml-cpu.c:1631-1685`），每 token 仅 8KB，压缩无意义
- **结论**：压缩不是杠杆。真正的浪费是专家串行让 DDR 延迟暴露，而不是字节数本身

## 五、如何逼近上界（按性价比排序）

1. **⭐专家间并行（理论最高 ROI，中风险）**：改 `ggml-cpu.c:1730-1785`，把外层逐专家串行改成"8 专家分给 8 线程并行"，让 8 个 1.72MB 读取重叠隐藏 DDR 延迟。这是唯一能从原理上解释 590% CPU 低 ALU 利用率的方向。**需改源码+重编译+交叉验证**
2. **提高 MoE cache 命中率**：cache 越大 miss 越少，但 8G 显存限制（1350MiB 已是上限）
3. **减少专家数量/宽度**：换模型（混合精度或更小 MoE），需用户决策
4. ❌ 搬专家到 GPU、压缩激活、开 pipeline：均已排除

## 七、一句话回答
**搬数据到 CPU（当前做法）代价最小，已是近零成本；权重再压缩是错的杠杆。真正浪费的是"8 个专家串行算"让 DDR 延迟暴露——如果要逼近上界，应该让专家并行、把 8 次冷读取重叠起来，而不是继续纠结搬什么或压多小。**
