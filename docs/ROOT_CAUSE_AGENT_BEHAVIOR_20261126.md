## 一、三层根因（8 个问题的归类）

### 第 1 层：验证层——检查器自身有 bug + 只查语法不查语义（最直接、最好修）

**表现**：问题 3（不会找 slot）、4（验证缺失）、7（语法错误反复）

**根因 A（机制自身制造问题，必须先修）**：子任务实证——5 次"语法错误 Cannot find module
...hardware-monitor-plugin/client.js" **全是假阳性**。模型写的是相对路径
`hardware-monitor-plugin/client.js`（文件真实存在于 workspace/default-workspace/），
但 harness 的 `execFileSync(node, ['--check', p])`（运行版 R:505-508）按**自己的 cwd =
`D:\Brain\dsh-data\profiles\desktop`** 解析 → 查了个不存在的路径。
同一个 cwd bug 还污染了 FEP 断言（`observed.fileExists=false` → `deviation=product-missing`）。
模型每次收到假错误去 read 那个不存在的路径，5 次循环——**这是机制逼出来的循环，不是模型不修**。

**根因 B**：`verify-on-edit`（P:1458-1466）只做 `node --check` / `py_compile` / yaml 解析。
但即使路径修对，今天的失败仍全是**语义级**：
- `sidebar.right.header.actions` 这个 slot 不存在 → 语法合法 → 静默忽略 → 按钮不显示
- `src='/ui/'` 是 404 → 语法合法 → 页面空白
- 相对路径 `./client` → 报了 4 次 Cannot find module，**只是 pendingInject 文本**，模型照写不误

**源头修复**：把"确定性检查"从语法扩到**可机械验证的语义**——
1. **slot 存在性**：写 client.js 后，从 app.asar grep `ctx.slots.inject('X')` 的 X 是否存在；
   不存在 → 不仅 pendingInject，而是 `verify-on-edit` 判 FAIL + 计入 D5 失败计数。
2. **路径存在性**：client.js / server 代码里出现的相对路径 `./xxx`、URL `/ui`，
   检查目标是否真实存在（文件 or HTTP 200）；不存在 → FAIL。
3. **失败升级**：语法/语义检查失败 N 次（N=2）后，从"提醒"升级为**硬拦截**——
   阻止本次 write 落入生产目录，改为写隔离副本 + 强制用户确认。

> 依据：SWE-bench 实验证明"每次编辑后验证" +15.6pp——但那是**语法**验证。
> 今天证明：先修验证器的 cwd bug（假阳性），再补语义验证，顺序不能反。

### 第 2 层：目标层——目标漂移 + 压缩丢线索（最顽固）

**表现**：问题 1（四次目标漂移）、8（5 次压缩后重新列开放问题）

**根因链**：
1. dsh 的 compaction 摘要在外部插件（`@deepseek-ai/dsh-compaction-basic`），
   harness 改不到摘要 prompt；
2. P0 存档的"开放问题"来自 `s.lastTodos`（模型显式写的 todo），
   但模型**没把"左侧入口"写进 todo**（它写的是"修复崩溃/连接失败"）；
3. 每次压缩后，真正的用户目标（`【初始任务】`）被挤到存档第一行，
   而模型按"最新指令"行动——最新指令是它自己的中间目标。
4. 今天部署的"防线2：未闭环纠错保留"只抓 reasoning 里的自我纠错句式，**抓不到用户目标漂移**。

**源头修复**：
1. **用户目标锚定**：存档注入里把 `s.initial`（初始任务）和 `s.latest`（最新用户指令）
   提升为**不可变的验收标准**——每轮 pre-step 都注入"你正在做的事是否仍在服务这个目标？
   若已切换目标，先说明为什么，否则回到原目标"。
2. **目标漂移守卫（零 LLM）**：检测 `s.latest` 与当前 todo/tool 目标的关键词覆盖率，
   低于阈值 → 注入"目标漂移告警"+ 计入 D5。**这不是拦模型思考，是让它显式声明目标变更**。
3. **压缩前后目标对比**：`compaction/summary` 事件到达时，把摘要里是否包含 `s.initial` 的关键词
   做机械比对；缺失 → 立即重新注入完整初始任务（不等下一次 pre-step）。

### 第 3 层：执行层——"知道但不做" + 放弃式完成（最深、最难）

**表现**：问题 2（承认 slot 无效但不改）、5（让用户 F12 粘代码后 completed）、6（重复探测循环）

**根因**：这是**软机制的固有上限**。所有 pendingInject 类提醒（D1-D5、审计、纠正器、
控制回合、停止条件）都是"给模型发文本"，模型可以：
- 读完后继续按自己的惯性走（今天 seq1402 承认 slot 无效，下一步却没改 client.js）
- 把工作甩给用户后声明 completed（14:57 "去 F12 粘代码" → turn/end completed）
- 在探测循环里打转（harness 报了 6 次"重复动作"，仍继续）

**源头修复**（从软到硬，按可行性排序）：
1. **present/turn 结束闸门加"未完成交付"检测**（零 LLM）：
   检测 assistant 正文含"请你/让用户/粘贴到控制台/手动执行/F12"且无对应工具调用结果 →
   **不允许 completed**，注入硬提示"这是未完成交付；要么自己验证，要么明确说卡在哪"。
2. **"承认问题但未修复"闭环守卫**（零 LLM，可机械做）：
   - 当 reasoning/正文出现"X 无效/不对/不是.../应该改成" → 记入 `s.openCorrections`（今天防线2已做）
   - **新增**：下一次 write/edit 的目标文件若与 X 相关，但内容未包含修正 → 判 FAIL，
     阻止"口头承认、行动不变"。
3. **重复探测的第 N 次强制换法**（已部分存在但触发太晚）：
   今天 read×4 / grep×3 / pwsh×6 都报了，仍是提醒。改为**第 3 次同参探测后，
   确定性执行器代做**（executeReadOnly 已有），把结果直接注入，模型不必再探测。
4. **模型能力边界要承认**：35B 在"如何在打包二进制里找 slot"这类问题上会卡——
   这是知识/方法缺口，靠提示无效。正解是 **skill 卡沉淀方法**（"查 DSH slot 用 grep -ao 扫 app.asar，
   不要用 glob 扫二进制"），让下次同类任务直接加载。

## 三、真正的源头：三条铁律

1. **凡是能机械验证的，绝不交给模型的判断**（slot 存在、路径存在、HTTP 200、语法）——
   做成确定性检查，失败就 FAIL，不是提醒。
2. **凡是软提醒，默认模型会忽略**（今天 trace 会证明）——
   提醒 N 次无效后必须升级为硬约束（代执行 / 阻止落盘 / 不允许 completed）。
3. **目标必须外置且不可被中间步骤覆盖**——
   用户目标存 `s.initial`，每轮对比，漂移就告警，压缩丢就重注。
