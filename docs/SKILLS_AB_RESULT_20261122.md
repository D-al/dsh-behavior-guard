# Skills 双轨 A/B 实验报告（2026-11-22）

> 触发：用户"测试一下，尤其是针对常用工具和不常用工具都有试试"
> 目标：对比自研关键词技能卡注入 ON vs OFF，看是否干扰常用工具、是否帮助低频工具

## 一、实验设计

- 模式 A = `skillsEnabled` 默认 true（自研关键词注入 ON）
- 模式 B = 运行版 `cordis.patch.yml` 加 `skillsEnabled: false`（OFF，官方 skill 工具仍在）
- 场景1「常用工具」：列 .py 文件 + grep def main + 写结果文件（触发 read/glob/grep/pwsh）
- 场景2「低频关键」：诊断 llama-server 卡死/OOM（命中 `debug-llama-server` 关键词）
- 通过 bridge 发真实任务到 dsh 35B（不走 projectlab 的直连 HTTP，那样测不到 harness 注入）
- 切换模式需重启 dsh（实测 start 10~50s）

## 三、能确认的结论（机制层）

1. **开关有效**：OFF 模式注入 0 次、ON 模式 2 次——配置覆盖真生效（这是之前 ADR-0028"配置改了不等于生效"担心的反面验证）。
2. **常用工具场景也触发注入**（核心发现）：场景1 任务文本含 "grep"/"read"，命中了 `tool-boundaries` 技能的关键词 → 注入 `tool-boundaries` 卡。
   - 这**实证了子任务harness调查的判断**：关键词命中过宽，自研注入与官方 skill 系统双轨且覆盖面重叠。
   - 但注意：注入内容本身（"相似工具怎么区分"）与任务相关，不能仅凭"触发了"就判为干扰。
3. **低频场景正确命中**：场景2 命中 `debug-llama-server`，说明关键词映射在它设计的目标场景上是准确的。
4. **官方 skill 工具调用 0 次**：两次实验模型都**没有主动调用官方 `skill` 工具**加载手册全文。
   - 这支持了"对 35B 弱模型，模型主动调用不如 harness 自动提醒可靠"的保留意见——但单次实验不能定论。

## 四、不能确认的结论（诚实标注）

1. **样本严重不平衡**：A 149 事件 / 19 工具调用，B 31 事件 / 3 工具调用。
   原因：B 的场景2 还没跑完就按"测完就关"的规矩停了 dsh；A 还包含了被 cancel 的后续任务。
   → **不能对比"谁更快/谁工具选得更准"**。
2. **单次实验**：项目铁律"判优至少 2 次"，本次每模式每场景仅 1 次。
3. **bridge events API 有分页截断**：早期注入事件被截掉，必须从会话 zstd 文件采集才完整（本报告的注入数据来自完整会话文件）。
4. **任务设计偏重**：场景1 要求写详细报告，35B 反复修正文件导致步骤多（A 出现 D1 重复探测守卫触发"pwsh×3"），这是**守卫机制**在工作，与 skills A/B 无关，但污染了工具调用计数。

## 五、净结论

**这次实验回答了"机制是否按设计工作"（是），但没有回答"哪套更好"（样本不足）。**

- 支持收敛 skills 双轨的证据：常用工具场景误触发注入（关键词过宽）+ 官方 skill 工具零调用（主动路径没跑通）
- 反对贸然收敛的证据：低频场景注入命中准确 + 35B 主动调用 skill 的可靠性未验证

**建议（待用户拍板）**：
1. 若要下定论，需做**受控重复实验**：同任务 × 每模式 ≥2 次 × 任务设计轻量化（只测工具选择、不写报告），并严格等任务自然结束
2. 短期可做的低风险动作：**收窄 `tool-boundaries` 的关键词**（去掉泛化的 "read"/"grep"，保留具体场景词），减少常用工具任务的误触发——这不改变架构，只调关键词
3. 不建议现在就拆掉自研注入——官方 skill 工具调用 0 次说明主动路径在本环境未验证
