## 2. dsh 犯的错误（17 条，按严重度）

### 致命级

**E1. 6 次写完全相同内容，空转 10 分 27 秒**
- 证据：sha `beed9c7e`（3780 字）在 seq2114/2132/2156/2172/2247/2267 连写 6 次
- 语义检查 4 次准确报出（"3/4/5/6 次相同"），但**每次报完下一次 write 仍是同哈希**
- 判定：**识别准确、阻止无效**

**E2. 说了 A 做 B（3 次）**

- 判定：**审计抓不到"言行不一致"** ← 机制空白

**E3. 双副本不同步却声称 SHA256 一致**
- seq2050 声称"源文件和安装目录 SHA256 一致 ✅"

**E4. 把验证工作推给用户（软甩锅）**

## 5. 发现的真正 bug（我今天同步机制的空壳问题）

这是本次审计最重要的技术发现：**我今天"同步"进运行版的两组机制，实际是死的**。

### bug 1：M3 patternLock 空壳
```js
if (cfg.patternLockTraceEnabled && s.toolWindow?.length >= 12) { ... }
```
- `s.toolWindow` **从来没有任何 push 点** → 永远 `undefined` → `?.length>=12` 恒 false
- 结果：`pattern_lock` 全程 0 次

### bug 2：工具失败自愈空壳（双重）
```js
const f = extractFailure(event, s.toolNamesById)   // s.toolNamesById 从未赋值
...
s.pendingHeal = f                                  // 置位了，但没人消费
```
- `s.toolNamesById` 没有赋值点 → `extractFailure` 拿不到工具名 → `tool_failure` 恒 0
- `s.pendingHeal` 没有消费点 → 即使置位也不会注入提示
- 结果：31 条 FAIL/UNPRODUCTIVE 一条都没接住

**这两处已修**（`patch_sync_mech_fix.py` + `patch_heal_inject.py`），补了 state 初始化、toolWindow push、toolNamesById 映射、goalRestatedStep 锚点、heal 注入点。代码已改、语法通过，**待下次重启生效**。

### 为什么会出现这个 bug
我同步时只照抄了"import + 调用点"，漏了"状态从哪来"。这正是项目铁律"文档宣称完成≠代码实际生效"的又一次现身——我不是被文档骗，是被自己的补丁骗了。

## 6. 问题总结（五条）

1. **所有软机制（mind_state/fep/control_turn/archive_dedup）都在"只报不拦"**，长任务里它们的存在感约等于噪音。`fep_cycle` 在空转时仍报"收敛"最典型。

2. **硬机制（safety_gate）能挡住结束，但给不出下一步**。16 次拦截的措辞从"请调用工具"升级到"这是未完成交付"，模型的行为是"再 read 一遍然后写同样的东西"——**它不知道具体该改什么**。

3. **审计只看得见"形式"（hash 相同、slot 存在、语法对），看不见"语义"（说 A 做 B、方案回退、虚假声称同步、全屏违反技能卡）**。4 条完全没人管的攻击全属此类。

4. **今天的两个"新同步机制"是空壳**——只加调用点不加状态来源。这提醒：同步机制的验收标准必须是"trace 里出现该 kind"，不是"代码里 grep 到了"。

5. **3 小时里 50% 是用户在等**（5553s/11046s），真正退化循环 1751s。而 turn13 用一条明确指令 10 分钟解决。**当前架构下，人的一次纠偏 > 审计的 16 次拦截。**
