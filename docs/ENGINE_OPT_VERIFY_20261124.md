## 流水线调研结论 + 带宽/搬移代价第一性原理修正（2026-11-23 晚）

> 用户两问：① 试改 scheduler 开流水线但保持 MoE cache 优势 ② 如何逼近带宽上界？搬专家还是搬数据代价最小？能否压缩后给 CPU 算？

### 一、流水线：调研后决定**不实施**（诚实结论）

两路独立源码分析一致，我认同：

#### 1.1 删 `llama-context.cpp:581` 那行不够
- pipeline 有 5 个前置条件（`:574-581`）：`n_devices()>1`、`n_gpu_layers>n_layer_all`、`split_mode==LAYER`、`offload_kqv`、`!has_tensor_overrides()`、`moe_cache_size==0`
- **生产两处独立不满足**：① 单 GPU → `n_devices()==1`（CPU 是 backend 不是 model device）；② 我们用 `--cpu-moe` → `has_tensor_overrides()` 为真
- 所以 pipeline 不是"被 MoE cache 单独挡住"，而是**本来就不适用于我们的单 GPU + CPU offload 场景**

#### 1.2 即使强开，decode 阶段也无效
- `llama-context.cpp:1831-1833`：graph reuse 时强制 `ggml_backend_sched_synchronize`——多轮 decode 复用图时 pipeline 自动失效
- 真正能重叠的只有"图内 split 重叠"（`ggml_backend.cpp:2155 prefetch_inputs`），它**不依赖 pipeline 且已经开启**，源码 `:2178-2182` 还特意为 copy callback 让路

#### 1.3 copy callback 与多 copy 硬冲突
- `llama-moe-cache.cpp:858` 注释自曝单 copy 假设；`:805-806` 的 `ggml_backend_synchronize(backend)` 是全 backend 同步，会把 4 个 copy 串行化
- 去掉同步则会静默读到被覆盖的 slot_map（**输出错误而非崩溃**，最难发现的那类 bug）

#### 1.4 收益/风险
- 理论上限 0-20%，实际大概率 0-10%；而本机 sd≈4 t/s，收益可能测不出来
- 风险：静默输出错误、cache 命中率下降、GGUF 兼容性
- **决定：不实施。** 这是"调研后决定不做"而非"失败"

### 二、带宽上界：我之前"带宽墙"的判断需要修正

#### 2.1 重算：MoE cache 命中后 DDR 流量很小
| cache 命中率 | miss 专家/token | DDR 读 | 34 t/s 时带宽 | 利用率(35-40GB/s) |
|---:|---:|---:|---:|---:|
| 0%（全 miss）| 320 | 550 MiB | 18.3 GB/s | 50% |
| 50% | 160 | 275 MiB | 9.1 GB/s | 23% |
| **70%** | 96 | 165 MiB | **5.5 GB/s** | **14%** |
| 85% | 48 | 83 MiB | 2.7 GB/s | 7% |

**如果 cache 命中率真是 70-85%，DDR 带宽只用了 7-14%，根本不是带宽墙。**（注：cache 命中率是估算，之前尝试用优雅退出拿 `llama_moe_cache:` 命中率日志但拿不到——`log_stats()` 只在析构打印，`terminate()` 强杀不触发。这是待补的证据。）

#### 2.2 真正的瓶颈：专家串行导致的延迟暴露
源码铁证（`ggml-cpu.c:1730-1785`）：
- 外层 `cur_a` **逐专家串行**，内层 8 线程只切分单个专家的 n_ff 输出行
- decode 时 `nr1=cne1=1`（每专家 1 token）→ `nchunk1=1`、`nchunk0=nth=8`
- 即：**8 个专家＝8 个串行 gemv 阶段**，每个阶段 8 线程协作
- 后果：每个专家的 1.72MB 权重读取是"冷启动"式随机访问，DDR 延迟无法被后续专家重叠 → CPU 线程在等内存，590% 占用但 ALU 只 7-10%

**这才是"带宽没打满但 CPU 满载"的解释：latency-bound，不是 bandwidth-bound。**

### 三、搬专家 vs 搬数据：代价对比（回答用户第二问）

| 方案 | 搬什么 | 每次量 | 代价 | 实测 |
|---|---|---|---|---|
| **搬数据到 CPU**（当前 share=1.0）| 激活（F32→Q8_K）| 2048×4B ≈ **8 KB** | 近零，权重本就在 DDR | ✅ 最优 |
| 搬专家到 GPU（share=0）| 专家权重 | **1.72 MB × miss 数** | PCIe 远慢于 DDR，8G 装不下 | ❌ 慢 28% |

**当前 share=1.0 已是代价最小的方案**——把极小的激活搬到 CPU，让巨大的权重原地不动。

### 四、压缩后给 CPU 算？

- **权重**：已是 q4_K（4.375 bpw），再降（Q3/Q2）质量风险大且收益不确定（见 Q3_K 调研）
- **激活**：ggml 已做 F32→Q8_K 转换（`ggml-cpu.c:1631-1685`），每 token 仅 8KB，压缩无意义
- **结论**：压缩不是杠杆。真正的浪费是专家串行让 DDR 延迟暴露，而不是字节数本身

### 五、如何逼近上界（按性价比排序）

1. **⭐专家间并行（理论最高 ROI，中风险）**：改 `ggml-cpu.c:1730-1785`，把外层逐专家串行改成"8 专家分给 8 线程并行"，让 8 个 1.72MB 读取重叠隐藏 DDR 延迟。这是唯一能从原理上解释 590% CPU 低 ALU 利用率的方向。**需改源码+重编译+交叉验证**
2. **提高 MoE cache 命中率**：cache 越大 miss 越少，但 8G 显存限制（1350MiB 已是上限）
3. **减少专家数量/宽度**：换模型（混合精度或更小 MoE），需用户决策
4. ❌ 搬专家到 GPU、压缩激活、开 pipeline：均已排除

### 六、待补的证据
- MoE cache 真实命中率（需优雅退出或加日志才能拿到）
- 专家并行的收益（需改代码实测）

### 七、一句话回答
**搬数据到 CPU（当前做法）代价最小，已是近零成本；权重再压缩是错的杠杆。真正浪费的是"8 个专家串行算"让 DDR 延迟暴露——如果要逼近上界，应该让专家并行、把 8 次冷读取重叠起来，而不是继续纠结搬什么或压多小。**

## 优化的理论上限在哪？怎么达到？（2026-11-24 凌晨）

> 用户问："优化的理论上限在哪？怎么才能达到上限？"
> 这一轮把此前 3 份文档里**互相矛盾**的"带宽墙 vs latency-bound"结论，用**实测带宽 + GGUF 精确字节账**统一了。

### 一、先把基础参数测准（之前文档用错了）

#### 1.1 DDR 带宽：实测 25.4 GB/s，不是文档假设的 35-40
用 numpy 大数组（512 MiB，远超 24MB L3）copy 7 次取中位：
```
copy (读+写): 27.0, 23.8, 22.7, 24.8, 25.4, 26.0, 26.8 -> 中位 25.4 GB/s
DDR4-3200 双通道理论: 51.2 GB/s -> 实测只达 50%
```
**此前所有文档用的"实用 35-40 GB/s"是高估**，导致上限被高估 ~40%。

#### 1.2 每 token 字节数：580 MiB（从真实 GGUF 元数据精算）
此前文档假设"每专家 1.72 MiB"，我解析了模型 GGUF 头部核实：
```
qwen35moe.expert_count=256, expert_used_count=8, expert_feed_forward_length=512
gate_exps: (2048,512,256) Q4_K(4.5bpw) = 576 KiB/专家/层
up_exps:   同上                          = 576 KiB/专家/层
down_exps: (512,2048,256) Q5_K(5.5bpw) = 704 KiB/专家/层
每专家每层 = 1856 KiB = 1.812 MiB
每 token = 8专家 × 40层 × 1.812 MiB = 580 MiB
```
文档假设 550 MiB，实际 580 MiB（差 5%，可接受）。

### 二、Roofline：上限取决于一个一直拿不到的未知数

| 场景 | 每 token DDR 流量 | 上限（实测 25.4 GB/s）| 当前 23 t/s 的带宽利用率 |
|---|---:|---:|---:|
| **全 miss**（cache 无用）| 580 MiB | **42 t/s** | **55%** |
| 命中 50% | 290 MiB | 84 t/s | 27% |
| 命中 70% | 174 MiB | 140 t/s | 16% |
| 命中 85% | 87 MiB | 280 t/s | 8% |

**MoE cache 命中率是决定性的**——它决定瓶颈是"带宽墙"还是"别的"。

- 若命中率接近 0 → 当前 23 t/s 已用掉 55% 带宽，**接近墙**，理论上限 42 t/s（还有 1.8x）
- 若命中率 70-85% → DDR 只用 8-16%，**远不是带宽墙**，瓶颈在别处（理论上限 >140 t/s，但实际受其它因素限制）

#### 命中率为什么拿不到（本轮又试了一次）
源码 `llama-moe-cache.cpp:864 log_stats()` 只在 `~impl()` 析构打印。本轮用 CTRL_BREAK_EVENT 让子实例退出（日志确认 `exited with status -1073741510`），但 router 直接清理，**析构没跑，命中率仍拿不到**。这是判定瓶颈的最后一块拼图，目前缺失。

### 三、矛盾的统一：为什么专家并行失败了

此前 `PIPELINE_RESEARCH` 文档断言：瓶颈是"专家串行导致 DDR 延迟暴露"，建议改成专家并行（本轮我实现了）。

**实测结果：专家并行慢 3-5%（t=-2.3~-3.0，20 次/配置双轮交叉，sd<1.2）。**

这推翻了"简单 latency-bound"的判断，说明：
- 即使存在 DDR 延迟暴露，**8 线程协作算一个专家的行级 ALU 并行度，比 8 个专家并行的延迟隐藏更有价值**
- 上游"专家串行 + 行级并行"是更优权衡（类似内存系统里"顺序访问 + 预取"优于"随机并行访问"）
- 所以瓶颈既不是纯带宽（55% 利用率还有空间），也不是纯延迟（并行化反慢），而是 **AVX2 解包+点积流水线与 DDR 供数的精细平衡**

### 四、理论上限到底在哪

分三层回答：

#### 4.1 硬上限（物理）
- **带宽硬顶**：DDR 实测 25.4 GB/s ÷ 580 MiB/token = **42 t/s**（无 cache）；理论带宽 51.2 则 84 t/s
- **算力硬顶**：2 GFLOP/token，AVX2 8 线程峰值 ~500 GFLOP/s → 250 t/s，**不是瓶颈**
- 结论：**带宽是物理上限，算力不是**

#### 4.2 结构上限（当前架构）
- MTP 投机解码已把有效吞吐从 23 → 30-35 t/s（接受率 0.83-1.0）
- spec 理论上限 = 1/(1-α) 当 draft 长度足够：α=0.9 → 10x，但受 draft 生成成本限制，实际 1.5-2x
- **当前 MTP 已接近实际收益天花板**（ drafter 本身要算）

#### 4.3 现实上限（本轮实测）
- 已采用：t8(+18%)、share=1.0(+28%)、MTP(+14~29%)、ctx-checkpoints(+23%)
- 已证伪：专家并行(-3~5%)、tiled(-60%)、q4_K 预取(0)、绑核(0/负)、编译裁剪(省磁盘不省显存)、Q8_0 视觉(省显存但 WDDM 看不出)
- **现实天花板：当前配置 30-35 t/s 已接近这套硬件+模型的结构性上限，剩余 1.3-1.5x 空间都在"减少字节"上**

### 五、怎么达到上限（按可行性和收益排序）

| 路径 | 理论收益 | 代价/障碍 | 可行性 |
|---|---:|---|---|
| **1. 提高 MoE cache 命中率** | 若命中率能从 50%→85%，DDR 流量减半 | 8G 显存限制，1350 MiB 已接近上限；需先拿到命中率数据 | ⚠️ 需先补证据 |
| **2. 混合精度专家（Q3_K 等）** | 每 token 字节 -25~33% → +30~50% | 质量风险；需重做 GGUF | ⚠️ 用户决策 |
| **3. 更激进的投机解码** | draft len 5→8、acceptance 提升 | MTP 头固定，改 draft 需重训/换模型 | ❌ 模型限制 |
| **4. 打开流水线并行** | 理论 1.3-1.4x | MoE cache copy callback 多 copy 冲突，实现风险高 | ❌ 调研后放弃 |
| **5. 专家并行（本轮尝试）** | 理论治 latency | **实测 -3~5%，已证伪** | ❌ 走不通 |
| **6. 指令级微调**（scale 解包/预取/tiled/绑核）| <5% | 全部实测证伪或在带宽墙上净负 | ❌ 到头 |

### 六、诚实结论

1. **硬上限**：带宽决定，无 cache 时 42 t/s（实测带宽），理论带宽下 84 t/s。当前含 MTP 已达 30-35 t/s，**距离硬上限 1.2-2.8x**
2. **真正卡点**：MoE cache 命中率未知（拿不到），导致无法判断是"接近带宽墙"还是"另有瓶颈"。但专家并行失败说明不是简单 latency 问题
3. **能做的只剩"减少字节"**：混合精度专家（Q3_K）是唯一还没试的大杠杆，但需用户接受质量风险
4. **没有免费午餐**：本轮把低成本方向全试遍了，剩下的都要付出质量或实现风险

### 六·五、独立调研复核 + MTP 关键补充（子任务）

独立调研用我给的实测参数重算，结论**完全一致**：`T_max = 25.4e9 / 6.082e8 = 41.8 t/s`、当前 14.0 GB/s = 上限的 55%、差 1.82×。补充了两个我报告里没算透的点：

#### A. 算术强度证明 batch=1 必然 bandwidth-bound
```
I(batch=1) = 2·N / D = 2FLOP/byte ÷ 0.5B每权重 ≈ 4 FLOP/byte
机器 ridge point = P_peak/B ≈ 500/25.4 = 19.7（保守 200/25.4=7.9）
I=4 ≪ ridge(8~20) → 必然访存瓶颈
翻过 ridge 需 batch≈2~5 —— 这解释了为什么只有"增大有效 batch"（投机解码/连续批处理）是软件侧突破 41.8 的路
```
当前算力 23×2N ≈ 56 GFLOP/s，CPU 峰值数百 GFLOP/s → **算力只用了 10% 左右，确认不是 compute-bound**。

#### B. MTP 投机解码的理论加速公式（关键洞察）
```
γ=每步 draft token 数, α=接受率, c=t_draft/t_target
E[每步产出] = (1−α^(γ+1))/(1−α)
加速比 S = E/(1+γc)
```
代入当前 α=0.83~1.0：

| γ | E(α=0.83) | E(α=1.0) | 提 α 的剩余空间 |
|---:|---:|---:|---:|
| 1 | 1.83 | 2.00 | **仅 +9.3%** |
| 2 | 2.52 | 3.00 | +19.1% |
| 3 | 3.09 | 4.00 | +29.4% |

**关键结论：α 已饱和（0.83–1.0），继续卷接受率最多 +9%；要空间只能加 γ（更多 MTP 头）。** γ=1→3 理论 1.7×，可把有效吞吐推到 ~39 t/s，接近 41.8 硬上限——因为它实质是把 batch 做大、翻过 ridge。

#### C. 路径排序（综合）
1. **补访存效率缺口**（14.0→25.4 GB/s，1.82×）——最大且最实，但最难（kernel/访存通路，本轮指令级微调全试过无效）
2. **MTP 加头 γ=1→3**（~1.7×，理论 ~39 t/s）——α 已到位条件成熟，但受模型 MTP 头数量限制（当前模型 `nextn_predict_layers=1`，很难加）
3. 降比特 Q4→Q3/Q2（字节减半，上限×2）——质量损失，非无损
4. 换更快 DDR——硬件，非软件路径
5. ❌ 专家并行/tiled/q4_K预取/绑核——已实测 ≤0，到头

**一句话**：瓶颈是带宽不是算力；软件侧先补访存效率缺口，再靠 MTP 加头把有效 batch 做大；其余已证伪的方向到此为止。

### 七、方法论沉淀
- **测量参数必须实测**：文档沿用的"DDR 35-40 GB/s"是高估，实测 25.4。基准参数错一个，整个 Roofline 结论都偏
- **矛盾结论要追到源头**：三份文档"带宽墙 vs latency-bound"吵了很久，根源是命中率这个未知数 + 带宽参数用错
- **证伪也是答案**：专家并行失败排除了最后一条"低成本治 latency"的路，让"减少字节"成为唯一剩余方向

## 一、访存效率缺口是什么

### 1.1 先把"缺口"量化出来（全部本机实测）

| 测量项 | 方法 | 结果 |
|---|---|---:|
| 硬件 STREAM 带宽（读+写）| numpy 大数组 copy，7 次中位 | **25.4 ~ 33.6 GB/s** |
| 单线程纯 memcpy | ctypes msvcrt.memcpy 256MiB | 8 ~ 14 GB/s |
| **decode 实际有效带宽** | 23 t/s × 0.608 GB/token | **14.0 GB/s** |
| DDR4-3200 双通道理论 | — | 51.2 GB/s |

**缺口 = 25.4 / 14.0 ≈ 1.8×**（保守取 STREAM 低值）。这就是"理论上限 41.8 t/s vs 当前 23 t/s"那个 1.82× 的物理来源。

### 1.2 关键实测：**不是访问模式的问题**

我原本以为 MoE 随机读 1.8MB 块会比顺序读慢很多。实测直接推翻：

```
专家池 2048 MiB，64 × 1.8MiB 块
顺序读: 11.0 GB/s
随机读: 10.8 GB/s
随机/顺序 = 0.99   ← 几乎完全一样
```

**原因**：1.8MB 的单块已经远大于预取器的有效视窗，顺序和随机对 DDR 来说都是"一大段流式"。所以"专家分散在 19GB 里导致随机访问"这个猜测**不成立**。

（注：sum 只有 11 GB/s 是因为 numpy 的 sum 有计算开销，不能当纯读带宽；纯拷贝能到 25-33。这里只用它做**相对比较**，相对结论有效。）

### 1.3 缺口的真正来源：**解包 ALU 堵住了内存流水线**

Q4_K 的 dot 不是"读一个数乘一个数"，每个 32 权重的 block 要做：
```c
memcpy(utmp, x[i].scales, 12);          // 复制 12 字节 scale
// 4 行位运算重组 6bit scale + 6bit min
_mm256_cvtepu8_epi16(...);              // 类型转换
4×2 次 _mm256_maddubs_epi16(...);       // 真正的 dot
```
**解包指令数 ≈ dot 指令数**——一半的 ALU 时间花在"把量化格式翻译成能算的数"上。

这完美解释了所有实测现象：
- **CPU 590% 占用但 ALU 利用率只 7-10%**：线程在等内存（stall），不是在算
- **但把专家并行（治延迟）反而慢 3-5%**：因为并行化后每个专家只剩 1 个线程算，行级并行度从 8 降到 1，解包+dot 的单线程吞吐本来就不够，延迟是藏住了但总时间更长
- **预取无效（t=0.59）**：数据预取来了，但解包 ALU 跟不上，数据在 L2 里等
- **tiled 慢 60%**：分块带来的额外索引/控制流开销，加在本已紧张的 ALU 上

**一句话**：缺口不是"带宽没打满"，也不是"随机访问慢"，而是**"解包计算与内存读取无法重叠"**——ALU 忙的时候，内存控制器在空转；内存喂数的时候，ALU 在等。两者串行，各占一半时间，所以利用率只有一半。

### 1.4 为什么难补（本轮已试遍）

要补这个缺口，必须让"解包 block N"和"预读 block N+1"重叠（软件流水线）。但：
- ggml 的 `ggml_vec_dot_q4_K_q8_K` 是紧循环，改成软件流水线要动 kernel 核心，且会打乱 MoE cache 的 buffer 布局
- 预展开 scale 表能省解包指令，但 scale 从 12 字节涨到 16 字节（+2.8% 带宽），在带宽紧张时净负
- 换 IQ 系列量化（查表解码）在无 AVX512 的 AVX2 上更慢（社区实测 IQ2_XS 70.3 vs Q2_0 93.8 t/s）

**结论**：这是当前硬件（AVX2 无 VNNI）+ 当前 kernel 结构（解包与 dot 串行）的**结构性上限**，不是某个开关能打开的。

## 二、MTP 能不能加头

### 2.1 直接结论：**不能加，但"加头"的功能已经存在**

#### 模型层面：加头不可行
- GGUF 元数据 `qwen35moe.nextn_predict_layers = 1`——模型训练时只有 1 个 MTP 头
- 这不是小 LM head，而是**一个完整的 Transformer 块**：n_embd=2048、ffn=6144、attn + 2 个 norm + eh_proj + shared_head_norm，**0.84B 参数 ≈ 0.5 GB**
- 源码 `src/models/qwen35moe.cpp:~524` 有硬性 `GGML_ASSERT(n_layer_nextn == 1)`——**多传一个 MTP 层会直接 assert 崩溃**
- 要真加头 = 训练新头权重（需要训练流程 + 数据），不是配置能解决的

#### 引擎层面："加头"的等价物 = `--spec-draft-n-max`
MTP 的 draft 是**自回归**的（源码 `common/speculative.cpp:~2113` 的 `while (n_drafting > 0)` 循环）：
```
用 1 个 MTP 头预测 token[1] → 把 token[1] 喂回去 → 预测 token[2] → ... 共 n_max 次
```
所以 `--spec-draft-n-max 6` 已经在做"同一个头连猜 6 个"。**加头的效果，调 n_max 就能得到**，不需要新头。

### 2.2 当前 n_max 已过最优，甚至偏大

从日志实测（1608 条 `draft acceptance` 记录）：
```
draft acceptance = 0.91892 (204 accepted / 222 generated), mean len = 3.24
draft acceptance = 0.91304 (126 accepted / 138 generated), mean len = 3.47
```
**acceptance 92%，但 mean len 只有 3.24**。

如果每位置都是 0.92，n_max=6 的理论期望接受长度 = `(1-0.92^7)/(1-0.92) = 5.5`。实测只有 3.24 → **说明第 3-4 位之后接受率暴跌**，后面 2-3 个 draft token 基本是白猜（多付验证成本、几乎不被接受）。

这与之前实测 `nmax=7 更慢（26.73 < 27.31）` 完全一致——**n_max 的收益在 4-5 附近就到顶了**。

#### 可做的微调（收益小）
- `n_max 6 → 4~5`：少 draft 2 个白费的 token，理论上省一点验证开销
- 但收益估计 <5%，而本机 sd≈4 t/s，**测不出来**。要测准必须看 `acc per pos`（需要 `-lv 4`）

### 2.3 顺手发现的两个配置缺陷

#### (a) ngram 那三个参数当前**完全无效**
autostart 传了：
```
--spec-ngram-simple-size-n 12 --spec-ngram-simple-size-m 32 --spec-ngram-simple-min-hits 2
```
但 `--spec-type` 只写了 `draft-mtp`（单个值）。**没有列出 ngram 类型，这几个参数就不会启用 ngram 投机**。

#### (b) `--spec-ngram-simple-min-hits` 本身是 no-op
源码 `common/speculative.cpp` 里 `min_hits` 只出现 6 次：3 次打印日志，第 6 次在 `common_ngram_map()` 里——那是 **ngram_map_k** 类型，不是 ngram_simple。**对 ngram-simple 类型完全没用到**。

所以 autostart 注释里写的"至少命中 2 次才提议，提高接受率"**从来没有生效过**。

#### (c) size_m=32 与 n_max=6 不匹配（如果真启用 ngram）
ngram_simple 的 `size_m` 是"每次起草长度"，`n_max` 是"最大验证 token"。如果 size_m=32 生效，会起草 32 个 token，而 n_max=6 只验证 7 个——**大部分 draft 白做**。注释说"默认48，收保守些"改成 32，仍然远超 n_max。

### 2.4 真正值得做的两件事

| 动作 | 收益 | 成本 |
|---|---|---|
| **1. 加 `-lv 4` 看 `acc per pos`** | 精确定位 n_max 拐点（是 3 还是 5） | 改日志级别+重启，零风险 |
| **2. 清理无效的 ngram 参数** | 无性能收益，但消除"以为它生效"的误解 | 改 autostart，低风险 |
| 3. n_max 调 4 或 5 试 | <5%，测不准 | 低 |
| 4. 真启用 ngram 投机（改 spec-type） | **不确定**：对代码重复多的场景可能有用，对自然语言通常没用 | 需 A/B，且与本机 agent 场景匹配度未知 |

### 2.5 诚实总结

- **"加头"在模型层面不可行**（1 个头是硬约束，源码 assert 锁死，加头=重训）
- **但功能上不需要加头**：`n_max` 已实现"同一个头连猜 N 个"，且当前 n_max=6 已经超过实测最优点（mean len 只 3.24）
- **想提升投机收益，唯一有意义的动作是用 `-lv 4` 看 `acc per pos` 找到真实拐点**，而不是盲目加 n_max 或加头
- 顺带发现 autostart 里 3 个 ngram 参数**全部无效**（spec-type 没启用 + min-hits 是 no-op + size_m 不匹配），是一处配置噪声

## 三、能不能换更小的 MTP 模型

### 3.1 MTP 头已经是量化过的，没有"降精度"空间

从 GGUF 实测 blk.40 的 20 个张量：
```
Q8_0 × 8（attn_q/k/v/output、eh_proj、shared 专家）
Q5_K × 1（ffn_down_exps）
Q4_K × 2（ffn_gate_exps、ffn_up_exps）
BF16 × 2（ffn_gate_inp）
F32 × 7（各种 norm）
```
**和主模型其它层的精度分布一样**（Q8_0 252 / Q4_K 78 / Q5_K 39）。所以"把 MTP 头量化得更小"——它已经是 Q4_K/Q8_0 了，再降只能到 Q3/IQ3，质量风险大且省得少。

### 3.2 MTP 贵的真正原因：它是完整的 256 专家 MoE 层
blk.40 不是小 LM head，而是**完整 Transformer 块**（0.84B 参数）：
- 每步 draft 要读 8 个专家（top8）× 1.86MiB ≈ **15 MiB 专家权重**
- 加非专家权重（attention 等），每步 draft 约 **0.5 GB 量级的读取**
- 而专家在 CPU（--cpu-moe 40），所以 **draft 和主模型抢同一块 DDR 带宽**

这解释了为什么 n_max 越大收益越小——每多 draft 一个 token，就多一次完整的 MoE 层前向，而第 4-5 位的命中率只有 0.05-0.18，投入产出严重倒挂。

### 3.3 可行的方向（按现实性排序）

| 方向 | 可行性 | 说明 |
|---|---|---|
| **A. 保持 nmax=5 不动** | ✅ 已确认 | 实测 24.56，与最优 nmax=3（25.09）无显著差异 |
| **B. 把 MTP 头搬上 GPU** | ⚠️ 显存不够 | 0.53 GB > 当前余量 ~0.46 GB。若强行搬会挤掉 MoE cache |
| **C. 用独立小 draft 模型（-md）** | ⚠️ 需词表匹配 | 需要一个与 35B 同词表的小模型；本机 9B 词表不一定一致，且需额外显存/内存 |
| **D. 换更小 MTP 头** | ❌ 不可行 | 只有 1 个头（源码 assert 锁死）、已是 Q4_K、加头=重训 |
| **E. 关掉 MTP 改用 ngram** | ❌ 已实测更慢 | ngram 对自然语言命中率低；MTP off 只有 19.98 t/s |

### 3.4 最值得试的一条：把 MTP 头搬上 GPU（受显存限制）

理论上：MTP draft 每步读 0.5GB 走 DDR，如果搬到 GPU（GDDR6 ~200+ GB/s），draft 成本大幅下降，n_max 可以调大，收益可能翻倍。

**但本机显存只剩 ~460 MiB，装不下 530 MB 的 MTP 头。** 除非：
- 牺牲 MoE cache（1350 MiB → ~800 MiB），可能得不偿失
- 只搬 MTP 的非专家部分（29MB），专家仍留 CPU——收益有限

#### ✅ 有价值的三条

**1. `nmax=2` 更省资源，且数据上等价**
源码 `common.h:417-428` 的 `need_n_rs_seq()` 直接返回 `n_max`——**nmax 决定分配多少 RS 状态**。nmax=3 比 2 多占状态，而实测收益差（1.18 t/s）vs sd（0.5-0.9）只有约 2σ，勉强显著。**保守可选 nmax=2**（省状态、更稳）。

`llama-quantize` 支持 `--tensor-type blk.40.*=q8_0`。当前这份 UD-Q4_K_XL 的 blk.40 已经是 Q8_0/Q4_K 混合（比主模型精度略高），是个好状态。**以后做量化时应该显式指定，防止它跟着主体一起掉到 Q4_K 拖累接受率**——这是"别让 MTP 变差"的具体做法。

**3. 9B 当 drafter 不可行，词表检查比想象严**
`common_speculative_are_compatible()`（speculative.cpp:108-171）要求：vocab_type 相同、bos/eos 的 id 相同、`|Δn_vocab| ≤ 128`、**且从 id 5 开始每个 token 的文本必须逐字节相同**（strcmp）。Qwen3.5-9B 与 3.6-35B 跨代，大概率不过。
即使过了也亏：9B **dense** 每 token 前向 ≈ 目标的 3 倍，而目标只激活 3B——经验法则是 **drafter 激活参数 ≤ 目标的 1/10**。本机 `Qwen3-0.6B-Q8_0.gguf`（639MB）量级合适，但同样要先过词表这关。

**4. ngram 可零成本旁挂（值得一试）**
`--spec-type draft-mtp,ngram-map-k4v`——多个类型可以同时启用，各自提供 draft 取最优。预期 **+0~5%，也可能为负**，但成本为零、随时可关。适合 agent 场景的 tool-call JSON 骨架、重复路径、代码块。

#### ⚠️ 一处需要纠正的说法

子任务从加速比反推"首令牌接受率约 40%"，**这与直接测量矛盾**（实测 acc per pos 第一位是 0.927）。它是用 `19.98→23.91` 的增幅倒推的，但那个反推假设了"验证成本不随 token 数增长"——而 **MoE 的验证成本接近线性增长**（每个 token 路由不同专家）。

正确算法：nmax=2 的期望产出 E=1+0.927+0.45=2.38，实际加速 1.197 → 验证成本是单 token 的 **1.99 倍**。即"验证 3 个 token ≈ 验证 1 个的 2 倍"，**MoE 几乎不摊薄权重读取**。这才是 MTP 收益远低于 dense 模型的根本原因。

| MTP 头搬 GPU（实验）| **24.74** | 1.40 |

**差 0.18 t/s = 0.7%，远小于 sd 波动 → 无显著差异。**

（附注：显存对照显示 `-ot` 实际只搬了约 160 MiB——464 MiB 的专家被 `--cpu-moe` 的正则抢先匹配走了。源码 `llama-model-loader.cpp:1328-1360` 是"先匹配先赢"带 `break`，而 `--cpu-moe` 的优先级高于 preset 里的 override。**但这不影响结论**，见下。）

### 三、为什么搬了也没用：draft 只占总计算的 0.6%

**关键计算**（这也是 MTP 对 MoE 加速远不及 dense 模型的原因）：

```
主模型每步（decode 1 token）：
  非专家权重读取 ≈ 2326 MiB
  + 该 token 路由的 8 个专家 ≈ 15 MiB
  ≈ 2415 MiB

MTP draft 每步：
  只读 8 个专家 ≈ 15 MiB（MTP 层只有 1 层，没有那 2326 MiB 的非专家大头）

draft 占主模型一步的比例 = 15 / 2415 ≈ 0.6%
```

**即使把 draft 的所有读取提速 8 倍（DDR 25 GB/s → GDDR6 200 GB/s），总时间也只省 0.5%。** 这与实测的 0.7%（噪声内）完全吻合。

#### 更深一层的洞察：MoE 的批量验证几乎不摊薄权重读取

dense 模型做投机解码，验证 γ+1 个 token 只读一次权重 → 接近 (γ+1)× 加速。
但 **MoE 的每个 token 路由到不同的专家**，验证 6 个 token 要读最多 48 个专家（89 MB）而不是 8 个（15 MB）——**专家读取接近线性增长**。

这解释了三个实测现象：
1. MTP 只带来 +25%（而非 dense 的 2-3×）
2. nmax=3 与 5 无显著差异（第 4-5 位接受率仅 5-18%，多读的专家不划算）
3. **优化 draft 本身（搬 GPU）没有意义**——瓶颈在"主模型要读多少专家"，不在"draft 快不快"

### 四、那 MTP 的 +25% 到底从哪来

不是"draft 便宜"，而是**主模型少跑了步**：
- 无 MTP：每产 1 token 要走一次主模型（2415 MiB 读取）
- 有 MTP（nmax=5, E≈2.8）：每步主模型验证一批，产出 2.8 token，但只付一次"非专家 2326 MiB"的读取
- **省的是那 2326 MiB 非专家权重的重复读取**，这部分才是真正被摊薄的

所以优化方向应该是"让每步验证更多有效 token"（提高接受率），而不是"让 draft 更快"。而接受率受限于只有 1 个 MTP 头、自回归误差累积——**这是训练问题，不是配置问题**。

### 五、如果一定要省显存，更划算的做法

| 方案 | 省 | 代价 | 评价 |
|---|---:|---|---|
| ctx 96K→60K | 292 MiB | 压缩提前到 33K，可用上下文少 30K | 与 MTP 无关，但确实能省 |
| MoE cache 1350→1000 | 350 MiB | 命中率略降（主模型会变慢） | 直接掉速，不划算 |
| 禁用视觉 | 858 MiB | 失去多模态 | 用户已明确要保留 |
| 降 ctx 到 60K + 砍 cache 到 1050 | 642 MiB | 双重代价 | 换来 0.7% 速度，完全不值 |

### 六、短答

**不能，或者说没意义。**
1. **60K 不够**：省 292 MiB 后余 192 MiB，低于安全线（450），接近必卡阈值（186）
2. **搬上去也没收益**：实测 +0.7%（噪声内）；理论上限 0.6%——因为 draft 只占总读取的 0.6%
3. **根本原因**：MoE 的批量验证不摊薄专家读取，MTP 的价值在"省非专家权重的重复读取"，不在"draft 快"
4. **要真正突破，只有重训多头 MTP / 换 EAGLE3 侧车**，那是训练任务

**建议：维持现状（96K ctx + MTP 在 CPU + nmax=5）。** 这已经是这套硬件上"不重训"条件下接近最优的组合。

## 牺牲视觉的 557 MiB 给谁最划算：MoE cache vs DFlash 侧车（2026-11-24 早）

> 用户问：拆掉视觉编码器牺牲多模态，把侧车装上去，能提升多少？如果不用侧车、改给专家缓存，又能提升多少？

### 结论先说：**两者都不如"单纯释放显存"**

| 557 MiB 的用法 | 实测 tps | 相对基线 |
|---|---:|---:|
| **禁用视觉，显存空着** | **25.96**（n=14） | **+4.9%（显著）** |

**禁用视觉本身能提速 4.9%，但把省下的显存给 cache 或侧车都不会更好——反而更差。** 收益来自"显存余量跨过安全线、消除换页"，而不是来自"多缓存了专家"或"多了一个 drafter"。

### 一、实验设计（分离变量）

三个变量：视觉开/关、cache 大小、DFlash 开关。逐个 A/B，每组 6-8 次取中位，每次独立重启（清 cache 状态）。

### 二、数据

#### 2.1 视觉开关 + cache 大小

| 配置 | 各次测量 | 中位 | 均值 | n | sd |
|---|---|---:|---:|---:|---:|

| **无视觉 + cache 1350** | 25.67, 26.25 | 25.96 | 25.96 | 14 | ~1.0 |
| 无视觉 + cache 1900 | 25.28 | 25.28 | — | 6 | 1.21 |

**无视觉 vs 基线：+1.22 t/s = +4.9%**，t ≈ 2.79（p<0.01，显著）。
**cache 1900 vs cache 1350（都无视觉）：−0.68 t/s**，反而略降（噪声内，但至少零收益）。

#### 2.2 DFlash 侧车（上一轮已测，此处并列）

| 配置 | tps | 相对基线 |
|---|---:|---:|
| DFlash 全 CPU（ngl=0）| 11.98 | −52% |
| DFlash 半 GPU（ngl=3）| 16.25 | −34% |

侧车 736 MiB BF16，即使禁用视觉（腾出 906 MiB）能全放 GPU（余 170 MiB，贴近必卡阈值 186），按 ngl=0→3 的 +35% 斜率外推，极限也就 21-23 t/s，仍低于 MTP 的 24.7。

### 三、为什么"禁用视觉"能提速 4.9%

**不是视觉计算本身慢（文本推理根本不走视觉），而是显存余量跨过了安全线。**

| 状态 | 显存余量 | 现象 |
|---|---:|---|
| 视觉开（基线）| **349 MiB** | 低于安全线 450，**偶发 WDDM 换页** → 测量里出现过 22.3 t/s 的掉速，sd 1.69 |
| 视觉关 | **906 MiB** | 远离安全线，无换页 → 波动小（sd 0.47-1.31）|

这与之前记录的规律完全一致：**"空闲 ≥450 MiB 才安全；186 MiB 必卡（WDDM 换页→1~2 t/s）"**。基线在 349 MiB 处处于"轻微换页"的灰色地带——平均损失约 5%，偶尔掉得更狠。

### 四、为什么给 cache 没用

MoE cache 从 1350 → 1900（+41%）**没有提速**，说明：

- **专家访问是长尾分布**：热点专家早就被 1350 MiB 覆盖了，新增的 550 MiB 缓存的全是冷门专家，几乎不命中
- 这也印证了之前的判断"1350 MiB 已接近上限"
- 加大 cache 还可能有副作用：更大的分配块 → 显存碎片略增，抵消了微小收益

**要真正提高命中率，需要的是"把热点专家按访问频率精确排序"（LRU 已接近最优），而不是"无脑加大容量"。**

### 五、为什么给侧车更差

DFlash 侧车 736 MiB 的读取量，在 CPU 上要和主模型抢同一条 DDR 带宽（25 GB/s，我们最稀缺的资源）。而 DFlash 的 block=16 让验证时要处理最多 16 个 token → MoE 每 token 路由不同专家 → 最多读 128 个专家（MTP nmax=5 只需 40 个）。**draft 抢带宽 + 验证成本线性增长，双重挤压。**


#### 如果需要保留多模态 → 维持现状
当前余量 349 MiB 虽在安全线下，但平均只损失 ~5%，可接受。若想两全，可考虑：
- 把 mmproj 从 F16 降到 Q8_0（省约 280 MiB）——收益约为禁用视觉的一半
- 或降低 ctx（60K 省 292 MiB），但会提前触发压缩

#### 不要做的事
- ❌ 加大 MoE cache（零收益）
- ❌ 装 DFlash 侧车（负收益）

### 七、一句话

**牺牲视觉能换来 +4.9%，但这个收益来自"显存别太挤"，而不是"腾出来给谁用"——给 cache 没用（热点已饱和），给侧车更糟（抢 DDR 带宽）。最优解是腾出来就空着。**
