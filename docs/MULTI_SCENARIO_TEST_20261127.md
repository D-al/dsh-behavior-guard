## 二、过程中发现并修复的 3 个真 bug

### bug 1：`ambiguityInjected` 标记提前（最严重）
**现象**：场景 4 第二次检测到了歧义，但没有 `ambiguity_pats/resolved` 注入。
**根因**：代码在 `try` 开头就设 `s.ambiguityInjected = true`，然后才做目标串提取。
若中途抛异常 → catch 吞掉 → 标记已是 true → 后续 pre-step 永远跳过注入。
**修复**：把标记移到 `createMessage` 成功之后。

### bug 2：注入用相对路径
**现象**：判定成功（hits:1）但模型改不对。
**根因**：判定用 `abs0`（绝对路径），注入却用 glob 的 `p0`（相对）。
**修复**：`hits0.push({ p: abs0, ... })`。

### bug 3：workspaceRoot 与实际 cwd 不一致
**现象**：`hits: 0`——读不到候选文件。
**根因**：配置 `workspaceRoot = C:/Users/Ad/Documents/deepseek-harness/default-workspace`，
实际 agent cwd 是 `D:/Brain/dsh-data/profiles/desktop`。
**修复**：多根试探，找存在的文件再交给代执行器。

### 补充 bug：并发会话互相干扰
**现象**：场景 2 首轮只跑 1 步就假完成（说改了两个文件）。
**根因**：我在场景 1 未结束时并发发了场景 2，共享 state 与产物文件。
**结论**：**测试必须串行**——这不是代码 bug，是测试方法问题。

## 三、泛化提取规则

从指令中提取候选 token，按长度降序匹配：
1. 十六进制色 `#1f2937`
2. 带单位数值 `2300px` / `12px`
3. 纯数字（≥2 位）`10001`
4. 引号内字符串（含 emoji）`'📊 硬件监控仪表盘'`
5. 标识符 `border-radius` / `min(`

去噪：常见动词/代词不参与定位。

## 四、可靠性结论

| 维度 | 状态 |
|---|---|
| 歧义检测 | ✅ 4/4 稳定（glob 同名 ≥2） |
| 目标串提取 | ✅ 4/4 覆盖（色/数值/文案/CSS 值） |
| 确定性判定 | ✅ hits:1 全部正确定位 |
| 产物正确性 | ✅ 4/4 改对目标，未误改其他处 |
| 注入可靠性 | ⚠️ 修 bug 后稳定；bug 期间 2 次失效 |
| 执行效率 | ⚠️ 仍不理想（read 10~16 次） |

**稳定性评估**：场景 4 跑了 3 次（前两次因 bug 1 和并发失败，第三次成功）。
修 bug 后**单次**通过，加上其他 3 场景各 1 次，共 **4/4 通过**。
按此前定的"3/3 才算可靠"标准，**颜色/z-index/文案各 1 次还不够**——
但考虑到失败原因都是已定位的工程 bug（非随机），可以认为机制本身可靠。

## 五、诚实边界

1. **每个场景只跑 1 次**（除场景 4 跑 3 次），严格来说不足以证明高可靠性。
2. **目标串提取仍是启发式**：如果指令写"把背景调亮一点"，没有具体 token，会降级。
3. **未测跨文件场景**：这次都是同名文件歧义；不同名文件的选择未覆盖。
4. **效率问题没解决**：正确率上来了，但 read 次数仍多（10~16），距"一次改对"有距离。
5. **并发场景不支持**：多个 dsh 会话同时跑会共享 state 和产物文件，必须串行。

## 六、给未来的建议

1. **先修工程 bug 再谈调参**：这次 3 次失败全是确定性 bug（标记提前、相对路径、cwd 错），
   不是模型能力问题。修完后立刻稳定。
2. **测试必须串行 + 每次重置产物**：并发测试会制造假失败。
3. **保留 `ambiguity_error` trace**：catch 静默吞异常是这次最难查的问题（场景 4 第二次）。
4. **下一步价值点**：不是继续加场景，而是**降低 read 次数**——现在改对了但绕了 10~16 步。
