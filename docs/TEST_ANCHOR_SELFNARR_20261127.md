# 实测报告：条件锚点 + 自述句注入（2026-11-27 00:20）

> 落地内容：chat template 条件锚点、闸门文案改自述句、两个结构 bug 修复。
> 测试样本：**改一个数值**（1 行修改）——比 turn12 更纯粹的对照组。

---

## 一、落地了什么

### 1. chat template 条件锚点（已部署，已验证加载）
`bench/chat_template_zh.jinja` 的 `add_generation_prompt` 分支：
```jinja
{%- set _gate = namespace(hit=false, seen=false) %}
{%- for _m in messages[::-1] %}
    {%- if not _gate.seen and _m.role == 'user' %}
        {%- set _gate.seen = true %}
        {%- if '[harness' in (_m.content | string) %}{%- set _gate.hit = true %}{%- endif %}
    {%- endif %}
{%- endfor %}
{%- if _gate.hit %}{{- '嗯，我得先确认刚才那次改动到底生效了没有，' }}
{%- else %}{{- '嗯，我需要' }}{%- endif %}
```
- jinja2 渲染验证：正常场景 → `嗯，我需要`；harness 场景 → `嗯，我得先确认刚才那次改动到底生效了没有，`
- llama-server `/props` 验证：模板已加载（64603 端口实例，含两处锚点）
- 成本：锚点在 `<think>` 之后 = prompt 最末尾；本模板不回填 reasoning → 动态切换不破坏前缀 cache

### 2. 闸门文案改自述句（已部署）
| 场景 | 旧（祈使句 + 外部身份） | 新（自述句） |
|---|---|---|
| 安全闸门 n≤2 | `[harness 安全闸门] 本轮不能结束（第N次）：…输出纯文本报告不算完成。下一步：调用工具修正…` | `[harness] 我刚检查了一下：…但产物还没真正改动。光写文字说明不算完成——我得直接改文件，或者跑一遍验证确认。` |
| 安全闸门 n≤5 | `…已连续拦截N次仍未修正。停止文字说明，立即调用…` | `我又检查了一遍（第N次）：…还是没真正改动产物。说明我一直在原地打转，得停下来换个做法。` |
| 安全闸门 n>5 | `…这是未完成交付；只有工具调用能解除拦截。不要再用文字声称完成。` | `这是第N次检查：…我一直没动手改。继续写说明没有意义，我需要立刻改文件。` |
| 交付闸门 | `检测到把工作甩给用户手动执行…这是未完成交付…` | `我刚发现自己在让你去手动操作…这其实是我该自己做的事。…我得自己调用工具验证` |

保留 `[harness` 前缀（模板锚点靠它识别纠正态）。

### 3. 修复两个结构 bug（真 bug，实测发现）

**bug A：continuations 短路吃掉 verify-on-stop**
`turn-stopping` 里 `if (state.continuations >= maxContinuationsPerTurn) return`（`maxContinuationsPerTurn=1`）
在 verify-on-stop 之前 → 一旦续跑过，verify 永久失效。加 `_needVerifyBypass` 例外。

**bug B（更严重）：安全闸门 return 导致后续闸门全跳过**
统一安全闸门一旦 steer 就 `return`，其后的 **verify-on-stop / handoff-gate 永远不执行**。
实测证据：6 次 safety_gate_block，但诊断打点 `diag_turnstop` **零输出**。
修复：在闸门之前先结算 `verifyFail` 并入 `hardFlags`，让一次 steer 同时携带"收尾验证缺失"。

## 二、实测结果：一个反直觉的发现

### 测试样本（刻意选最简单的）
"把 client.js 里浮动窗口的宽度从 960px 改成 800px。改完就行。"
—— 1 行修改，无歧义，无外部依赖。

### 实际发生了什么

| 指标 | 数值 |
|---|---|
| 工具调用总数 | **55 次** |
| 其中 `read` | **37 次** |
| `grep` | 8 次 |
| `pwsh` | 4 次 |
| `edit`（真正改文件） | **3 次** |
| `safety_gate_block` | **6 次** |
| `control_turn` | **10 次** |
| `mind_state`（重复动作） | 3 次（`read client.js ×6`、`×10`） |
| `d1_probe_guard` | 3 次 |
| 结果 | **未完成**（我手动 cancel） |

**改一个数值，55 次工具调用、37 次读同一个文件、6 次被闸门拦，依然没完成。**

### 机制全部在工作，但都无法让它停下

- `control_turn` 触发 **10 次** —— 我今天加的"连续 6 步无 write 强制触发"旁路**确实生效了**（审计里 21 分钟退化期是 0 次）
- `mind_state` 准确报出 `read client.js ×6` / `×10`
- `safety_gate_block` 6 次，文案已经是新的自述句
- `d1_probe_guard` 3 次

**但模型收到这些提示后，行为没有改变。**

## 三、三层结论

### 第一层：锚点和文案改动"已部署且机制正常"，但**没有可观测的行为改善**

这不是失败，而是暴露了更根本的问题：**在"永不结束"的空转里，闸门根本没有介入的机会**。
- 闸门挂在 `turn-stopping`（模型"想结束"时）
- 但模型陷入的是 `step` 循环（read → read → read），**它从不想结束**
- 所以闸门、verify-on-stop、handoff 全部轮不到

### 第二层：这是"识别 ≠ 阻止"的最纯粹证据

turn12 还能说"任务本身模糊"。这次任务只有一句话、一个数值，**没有任何借口**。55 次调用说明：
- 机制能准确识别（mind_state 报 ×10、控制回合 10 次）
- 但识别之后，**模型依然原地打转**

### 第三层：今天修的两个 bug 都是"闸门被绕过"，不是"闸门不够多"

- bug A：continuations 短路 → verify 永久失效
- bug B：安全闸门 return → 后续所有闸门跳过

**这解释了审计里"handoff 2 次全放行"和"16 次拦截 0 次改变方案"——不是闸门不生效，是大部分闸门根本没机会执行。**

## 四、诚实边界

1. **锚点的实际效果未能独立验证**：本次闸门触发时，模型是否真的被"纠正态锚点"影响，无法从输出中区分（它本来就在空转）。需要更精细的实验（对比同一提示下有无锚点的首 token 分布）。
2. **测试样本可能"过于简单反而更易空转"**：任务太小时模型可能不确定"是否改对了"，导致反复 read 确认。这与 turn12 的"任务模糊"是不同机制，不能完全等同。
3. **文案改动的主观效果无法量化**：6 次拦截仍是同样结果，只能说"没变差"，不能说"新文案无效"——因为对照基线（旧文案）在同一任务下的表现未测。
4. **两个 bug 修复尚未验证**（改完就写报告了）：`_needVerifyBypass` 和 pre-gate verify 都需要再跑一次才能确认生效。
5. **单次结果 ±10%**，55 次调用是极端值，但它至少证明"简单任务也会空转"。
