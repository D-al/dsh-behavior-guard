# 优化的理论上限在哪？怎么达到？（2026-11-24 凌晨）

> 用户问："优化的理论上限在哪？怎么才能达到上限？"
> 这一轮把此前 3 份文档里**互相矛盾**的"带宽墙 vs latency-bound"结论，用**实测带宽 + GGUF 精确字节账**统一了。

## 一、先把基础参数测准（之前文档用错了）

### 1.1 DDR 带宽：实测 25.4 GB/s，不是文档假设的 35-40
用 numpy 大数组（512 MiB，远超 24MB L3）copy 7 次取中位：
```
copy (读+写): 27.0, 23.8, 22.7, 24.8, 25.4, 26.0, 26.8 -> 中位 25.4 GB/s
DDR4-3200 双通道理论: 51.2 GB/s -> 实测只达 50%
```
**此前所有文档用的"实用 35-40 GB/s"是高估**，导致上限被高估 ~40%。

### 1.2 每 token 字节数：580 MiB（从真实 GGUF 元数据精算）
此前文档假设"每专家 1.72 MiB"，我解析了模型 GGUF 头部核实：
```
qwen35moe.expert_count=256, expert_used_count=8, expert_feed_forward_length=512
gate_exps: (2048,512,256) Q4_K(4.5bpw) = 576 KiB/专家/层
up_exps:   同上                          = 576 KiB/专家/层
down_exps: (512,2048,256) Q5_K(5.5bpw) = 704 KiB/专家/层
每专家每层 = 1856 KiB = 1.812 MiB
每 token = 8专家 × 40层 × 1.812 MiB = 580 MiB
```
文档假设 550 MiB，实际 580 MiB（差 5%，可接受）。

## 二、Roofline：上限取决于一个一直拿不到的未知数

| 场景 | 每 token DDR 流量 | 上限（实测 25.4 GB/s）| 当前 23 t/s 的带宽利用率 |
|---|---:|---:|---:|
| **全 miss**（cache 无用）| 580 MiB | **42 t/s** | **55%** |
| 命中 50% | 290 MiB | 84 t/s | 27% |
| 命中 70% | 174 MiB | 140 t/s | 16% |
| 命中 85% | 87 MiB | 280 t/s | 8% |

**MoE cache 命中率是决定性的**——它决定瓶颈是"带宽墙"还是"别的"。

- 若命中率接近 0 → 当前 23 t/s 已用掉 55% 带宽，**接近墙**，理论上限 42 t/s（还有 1.8x）
- 若命中率 70-85% → DDR 只用 8-16%，**远不是带宽墙**，瓶颈在别处（理论上限 >140 t/s，但实际受其它因素限制）

### 命中率为什么拿不到（本轮又试了一次）
源码 `llama-moe-cache.cpp:864 log_stats()` 只在 `~impl()` 析构打印。本轮用 CTRL_BREAK_EVENT 让子实例退出（日志确认 `exited with status -1073741510`），但 router 直接清理，**析构没跑，命中率仍拿不到**。这是判定瓶颈的最后一块拼图，目前缺失。

## 三、矛盾的统一：为什么专家并行失败了

此前 `PIPELINE_RESEARCH` 文档断言：瓶颈是"专家串行导致 DDR 延迟暴露"，建议改成专家并行（本轮我实现了）。

**实测结果：专家并行慢 3-5%（t=-2.3~-3.0，20 次/配置双轮交叉，sd<1.2）。**

这推翻了"简单 latency-bound"的判断，说明：
- 即使存在 DDR 延迟暴露，**8 线程协作算一个专家的行级 ALU 并行度，比 8 个专家并行的延迟隐藏更有价值**
- 上游"专家串行 + 行级并行"是更优权衡（类似内存系统里"顺序访问 + 预取"优于"随机并行访问"）
- 所以瓶颈既不是纯带宽（55% 利用率还有空间），也不是纯延迟（并行化反慢），而是 **AVX2 解包+点积流水线与 DDR 供数的精细平衡**

## 四、理论上限到底在哪

分三层回答：

### 4.1 硬上限（物理）
- **带宽硬顶**：DDR 实测 25.4 GB/s ÷ 580 MiB/token = **42 t/s**（无 cache）；理论带宽 51.2 则 84 t/s
- **算力硬顶**：2 GFLOP/token，AVX2 8 线程峰值 ~500 GFLOP/s → 250 t/s，**不是瓶颈**
- 结论：**带宽是物理上限，算力不是**

### 4.2 结构上限（当前架构）
- MTP 投机解码已把有效吞吐从 23 → 30-35 t/s（接受率 0.83-1.0）
- spec 理论上限 = 1/(1-α) 当 draft 长度足够：α=0.9 → 10x，但受 draft 生成成本限制，实际 1.5-2x
- **当前 MTP 已接近实际收益天花板**（ drafter 本身要算）

### 4.3 现实上限（本轮实测）
- 已采用：t8(+18%)、share=1.0(+28%)、MTP(+14~29%)、ctx-checkpoints(+23%)
- 已证伪：专家并行(-3~5%)、tiled(-60%)、q4_K 预取(0)、绑核(0/负)、编译裁剪(省磁盘不省显存)、Q8_0 视觉(省显存但 WDDM 看不出)
- **现实天花板：当前配置 30-35 t/s 已接近这套硬件+模型的结构性上限，剩余 1.3-1.5x 空间都在"减少字节"上**

## 五、怎么达到上限（按可行性和收益排序）

| 路径 | 理论收益 | 代价/障碍 | 可行性 |
|---|---:|---|---|
| **1. 提高 MoE cache 命中率** | 若命中率能从 50%→85%，DDR 流量减半 | 8G 显存限制，1350 MiB 已接近上限；需先拿到命中率数据 | ⚠️ 需先补证据 |
| **2. 混合精度专家（Q3_K 等）** | 每 token 字节 -25~33% → +30~50% | 质量风险；需重做 GGUF | ⚠️ 用户决策 |
| **3. 更激进的投机解码** | draft len 5→8、acceptance 提升 | MTP 头固定，改 draft 需重训/换模型 | ❌ 模型限制 |
| **4. 打开流水线并行** | 理论 1.3-1.4x | MoE cache copy callback 多 copy 冲突，实现风险高 | ❌ 调研后放弃 |
| **5. 专家并行（本轮尝试）** | 理论治 latency | **实测 -3~5%，已证伪** | ❌ 走不通 |
| **6. 指令级微调**（scale 解包/预取/tiled/绑核）| <5% | 全部实测证伪或在带宽墙上净负 | ❌ 到头 |

## 六、诚实结论

1. **硬上限**：带宽决定，无 cache 时 42 t/s（实测带宽），理论带宽下 84 t/s。当前含 MTP 已达 30-35 t/s，**距离硬上限 1.2-2.8x**
2. **真正卡点**：MoE cache 命中率未知（拿不到），导致无法判断是"接近带宽墙"还是"另有瓶颈"。但专家并行失败说明不是简单 latency 问题
3. **能做的只剩"减少字节"**：混合精度专家（Q3_K）是唯一还没试的大杠杆，但需用户接受质量风险
4. **没有免费午餐**：本轮把低成本方向全试遍了，剩下的都要付出质量或实现风险

## 七、方法论沉淀
- **测量参数必须实测**：文档沿用的"DDR 35-40 GB/s"是高估，实测 25.4。基准参数错一个，整个 Roofline 结论都偏
- **矛盾结论要追到源头**：三份文档"带宽墙 vs latency-bound"吵了很久，根源是命中率这个未知数 + 带宽参数用错
- **证伪也是答案**：专家并行失败排除了最后一条"低成本治 latency"的路，让"减少字节"成为唯一剩余方向
