## 2. 为什么选"结构重组 + 止血"而非彻底重绘

三个方案对比后选 B：

- **A 三层分文件**（导航/真相/归档分离）：收益最大，但要改执行器路径 + README/docs 全部引用 + 三副本一致性，改动面过大，当前 agent 已退化、不宜大改。
- **B 结构重组 + 止血（选定）**：保留 §1-§8 章节号（README 6 个锚点不断），把机器块移到文末附录 A；修过时数字、断链、承重 bug。风险低、收益大。
- **C 只止血**：最保守，但人读体验（700 行 YAML 挡在前面）不解决。

## 5. 沉淀的教训

1. **活文档的结构本身就是维护成本**：把机器真相塞在正文开头，看似"权威优先"，实际让人读体验崩塌且漂移高发。正确做法是人读在前、机器块在末附录，两者靠标记定位解耦。
2. **重排结构前先查外部锚点**：README 有 6 个锚点指向章节号/标题——不动章节号是零断链的关键。
3. **"同一数据存在两处"必出错**：test_sids 在顶层和 meta 各一份、执行器只读其一——这是这次最贵的 bug。修法是**双写 + 读取端兼容**。
4. **数字类内容（trace 行数、完成计数）要在机器块和正文同时更新**——否则人读与机器读得出不同结论。
