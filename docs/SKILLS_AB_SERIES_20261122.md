## Skills 双轨 A/B 实验报告（2026-11-22）

> 触发：用户"测试一下，尤其是针对常用工具和不常用工具都有试试"
> 目标：对比自研关键词技能卡注入 ON vs OFF，看是否干扰常用工具、是否帮助低频工具

### 一、实验设计

- 模式 A = `skillsEnabled` 默认 true（自研关键词注入 ON）
- 模式 B = 运行版 `cordis.patch.yml` 加 `skillsEnabled: false`（OFF，官方 skill 工具仍在）
- 场景1「常用工具」：列 .py 文件 + grep def main + 写结果文件（触发 read/glob/grep/pwsh）
- 场景2「低频关键」：诊断 llama-server 卡死/OOM（命中 `debug-llama-server` 关键词）
- 通过 bridge 发真实任务到 dsh 35B（不走 projectlab 的直连 HTTP，那样测不到 harness 注入）
- 切换模式需重启 dsh（实测 start 10~50s）

### 二、实际执行

| 项 | A-ON | B-OFF |
|---|---|---|
| 会话 sid | `session-b1a5f754…` | `session-ce3472b3…` |
| 事件数 | 149 | 31 |
| 工具调用 | 19 | 3 |
| **技能卡注入次数** | **2** | **0** |
| 注入的卡 | ① `tool-boundaries`（场景1）② `debug-llama-server`（场景2）| 无 |
| 官方 skill 工具调用 | 0 | 0 |
| 工具分布 | edit5/read5/pwsh4/write2/glob1/grep1/todo1 | glob1/grep1/pwsh1 |

### 三、能确认的结论（机制层）

1. **开关有效**：OFF 模式注入 0 次、ON 模式 2 次——配置覆盖真生效（这是之前 ADR-0028"配置改了不等于生效"担心的反面验证）。
2. **常用工具场景也触发注入**（核心发现）：场景1 任务文本含 "grep"/"read"，命中了 `tool-boundaries` 技能的关键词 → 注入 `tool-boundaries` 卡。
   - 这**实证了子任务harness调查的判断**：关键词命中过宽，自研注入与官方 skill 系统双轨且覆盖面重叠。
   - 但注意：注入内容本身（"相似工具怎么区分"）与任务相关，不能仅凭"触发了"就判为干扰。
3. **低频场景正确命中**：场景2 命中 `debug-llama-server`，说明关键词映射在它设计的目标场景上是准确的。
4. **官方 skill 工具调用 0 次**：两次实验模型都**没有主动调用官方 `skill` 工具**加载手册全文。
   - 这支持了"对 35B 弱模型，模型主动调用不如 harness 自动提醒可靠"的保留意见——但单次实验不能定论。

### 四、不能确认的结论（诚实标注）

1. **样本严重不平衡**：A 149 事件 / 19 工具调用，B 31 事件 / 3 工具调用。
   原因：B 的场景2 还没跑完就按"测完就关"的规矩停了 dsh；A 还包含了被 cancel 的后续任务。
   → **不能对比"谁更快/谁工具选得更准"**。
2. **单次实验**：项目铁律"判优至少 2 次"，本次每模式每场景仅 1 次。
3. **bridge events API 有分页截断**：早期注入事件被截掉，必须从会话 zstd 文件采集才完整（本报告的注入数据来自完整会话文件）。
4. **任务设计偏重**：场景1 要求写详细报告，35B 反复修正文件导致步骤多（A 出现 D1 重复探测守卫触发"pwsh×3"），这是**守卫机制**在工作，与 skills A/B 无关，但污染了工具调用计数。

### 五、净结论

**这次实验回答了"机制是否按设计工作"（是），但没有回答"哪套更好"（样本不足）。**

- 支持收敛 skills 双轨的证据：常用工具场景误触发注入（关键词过宽）+ 官方 skill 工具零调用（主动路径没跑通）
- 反对贸然收敛的证据：低频场景注入命中准确 + 35B 主动调用 skill 的可靠性未验证

**建议（待用户拍板）**：
1. 若要下定论，需做**受控重复实验**：同任务 × 每模式 ≥2 次 × 任务设计轻量化（只测工具选择、不写报告），并严格等任务自然结束
2. 短期可做的低风险动作：**收窄 `tool-boundaries` 的关键词**（去掉泛化的 "read"/"grep"，保留具体场景词），减少常用工具任务的误触发——这不改变架构，只调关键词
3. 不建议现在就拆掉自研注入——官方 skill 工具调用 0 次说明主动路径在本环境未验证

### 六、实验纪律遵守情况
- dsh 按需：实验前 start、结束 stop，实测 llama 残留 0、配置已恢复原样
- 配置回滚点：`D:/Brain/_cleanup_20261118/cordis.patch.before_skills_ab.yml`
- 证据只认真实 sid 的会话文件事件，不用关键词计数冒充

## Skills 双轨受控重复实验报告（2026-11-22 第二版）

> 触发：用户"做受控重复实验：同任务 × 每模式 ≥2 次 × 任务轻量化（只测工具选择不写报告），严格等任务自然结束"
> 相对第一版（docs/SKILLS_AB_RESULT_20261122.md）修正：新会话每次重建、轻量任务、严格自然结束判据、样本均衡

### 一、实验设计

| 项 | 设计 |
|---|---|
| 模式 A (ON) | 默认 `skillsEnabled: true`，关键词命中即注入技能卡 |
| 模式 B (OFF) | 运行版 cordis.patch.yml 加 `skillsEnabled: false`，官方 skill 工具保留 |
| 场景 common | "用 glob 列 test_*.py 文件，直接告诉我数量"——1 步工具调用，不写文件 |
| 场景 rare | "用 pwsh 查有没有 llama-server 进程（排查卡死/OOM 第一步）"——命中 `debug-llama-server` 关键词 |
| 每格样本 | ≥2（实际 ON/common 4、ON/rare 2、OFF/common 3、OFF/rare 2）|
| 会话隔离 | **每个 run 新建会话**——技能卡 per-session 只注入一次，同会话第二次会假阴性 |
| 自然结束判据 | `turn/end(reason.kind=completed)` 出现；超时 180s 记失败 |
| 证据源 | **会话文件 session.v4.jsonl.zstd**（bridge events 有分页截断，不可靠）|

### 二、结果（权威统计，从 11 个会话文件重建）

| 模式 | 场景 | n | inject 均值 | 工具调用均值 | 自然结束 | 工具选择 |
|---|---|---|---|---|---|---|
| ON | common | 4 | **1.00** | 2.0 | 4/4 | glob×4（其中1次追加pwsh）|
| ON | rare | 2 | **1.00** | 1.0 | 2/2 | pwsh×2 |
| OFF | common | 3 | **0.00** | 2.3 | 2/3 | glob×3（其中1次追加pwsh×3，未结束）|
| OFF | rare | 2 | **0.00** | 1.0 | 2/2 | pwsh×2 |

（1 个 OFF/common 会话未自然结束：模型 glob 后又调 pwsh×3，被纠正器介入——保留为失败样本，不删）

### 三、结论

#### 能下的结论（这次样本够）

1. **开关确实生效**：ON 每 run 注入 1 张卡、OFF 每 run 0 张——配置覆盖真实作用于运行时。
2. **两种轻量任务的工具选择在 ON/OFF 下完全一致**：
   - common 都是 glob（偶尔追加 pwsh），rare 都是 pwsh
   - **关键词技能卡注入没有改变工具选择**——至少在这两个场景、这个样本量下
   - 这是对"自研注入是否干扰常用工具"的直接回答：**没有观察到干扰**
3. **注入触发准确**：common 场景命中 `tool-boundaries`（因为任务提到 glob/test_*.py），rare 场景命中 `debug-llama-server`，都符合关键词设计。结合第一版"常用任务也误触发"的发现，说明关键词覆盖面宽，但**宽覆盖并未造成工具选择偏差**。

#### 不能下的结论（诚实标注）

1. **不能证明注入"有用"**：因为 OFF 组工具选择一样好（都是 1 步完成）。注入既没帮上忙，也没帮倒忙——在这两个轻量场景里它是**中性**的。
2. **不能推广到复杂任务**：轻量任务 1 步就结束，没有给技能卡发挥作用的空间。第一版复杂任务（写报告）里模型也**没有调用 skill 工具读手册**（官方 skill 路径 0 调用），所以"注入到底有没有被模型用上"仍未验证。
3. **样本仍小**：每格 2-4 次，35B 单次波动大（有 2/11 会话陷入多步）。要提高置信度需每格 ≥5 次。
4. **runner 的 wait 判据有 bug（已记录）**：run 命令的 wait_natural_end 在部分会话漏记，所以最终统计**直接从会话文件重建**（`rebuild` 命令）——证据源是会话文件，不是 runner 日志。

### 四、净建议（相对第一版更新）

- 第一版建议"收窄 tool-boundaries 关键词"——本受控实验显示**注入并未改变工具选择**，所以误触发的代价可能只是几行 token，**收窄的紧迫性下降**；可做但不是必须。
- **不建议拆掉自研注入**：OFF 组没有更好，ON 组没有更差；且官方 skill 工具调用 0 次，主动路径未验证。保持现状是零风险选择。
- 若还想深挖，下一个实验应测**复杂任务下注入是否被模型真正读用**（看有没有 read 技能手册全文的动作），而不是简单任务的工具选择。

### 五、实验纪律
- dsh 按需：实验前 start、结束 stop；配置恢复原样（回滚点 `cordis.patch.before_skills_ab.yml`）；llama 残留 0
- 证据只认真实会话文件的 tool/call 与 turn/end 事件，不靠 trace 关键词计数
- 失败样本保留不删（OFF/common 1 个未结束会话计入统计）
