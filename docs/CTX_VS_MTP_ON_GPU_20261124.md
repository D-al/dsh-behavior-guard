# 能否用 60K 上下文换 MTP 头搬 GPU？（2026-11-24 凌晨）

> 用户提议：降低 ctx（如 60K）腾出显存，把 MTP 头（blk.40）搬上 GPU，换取投机解码加速。

## 结论：**不值得。收益上限约 0.6%，实测 0.7%（噪声内），而代价是可用上下文少 30K。**

---

## 一、显存账：60K 根本不够

当前 8188 MiB 总量、已用 7784、余 404。MTP 头（blk.40）实测 **504 MiB**（其中专家 464 MiB、非专家 40 MiB）。

按 KV 随 ctx 线性推算（96K ≈ 780 MiB）：

| ctx | KV | 省下 | 装 MTP 后余量 | 判定 |
|---|---:|---:|---:|---|
| 98304（当前）| 780 | 0 | **−100** | 必卡 |
| 81920 | 650 | 130 | 30 | 必卡 |
| 73728 | 585 | 195 | 95 | 必卡 |
| 65536 | 520 | 260 | 160 | 必卡 |
| **61440（60K）** | **488** | **292** | **192** | **危险**（<安全线 450，接近必卡的 186）|
| 49152 | 390 | 390 | 290 | 危险 |
| 32768 | 260 | 520 | 420 | 临界 |
| ~28987 | 229 | 551 | 450 | 才安全 |

**要用 60K 换，必须同时砍 MoE cache**（1350→1050 才够）。而 60K ctx 还有个副作用：压缩触发点从 54K 提前到 **33K**（`min(61440×0.55, 61440−8192−16384)`），长任务会频繁压缩。

## 二、实测：搬上去也没收益

为了纯净测量，先临时禁用视觉（腾 858 MiB），把 MTP 头搬 GPU，跑同样的 2K prompt / 200 token / 6 次：

| 配置 | tps 中位 | sd |
|---|---:|---:|
| 基线（MTP 在 CPU，96K）| **24.56** | 0.56 |
| MTP 头搬 GPU（实验）| **24.74** | 1.40 |

**差 0.18 t/s = 0.7%，远小于 sd 波动 → 无显著差异。**

（附注：显存对照显示 `-ot` 实际只搬了约 160 MiB——464 MiB 的专家被 `--cpu-moe` 的正则抢先匹配走了。源码 `llama-model-loader.cpp:1328-1360` 是"先匹配先赢"带 `break`，而 `--cpu-moe` 的优先级高于 preset 里的 override。**但这不影响结论**，见下。）

## 三、为什么搬了也没用：draft 只占总计算的 0.6%

**关键计算**（这也是 MTP 对 MoE 加速远不及 dense 模型的原因）：

```
主模型每步（decode 1 token）：
  非专家权重读取 ≈ 2326 MiB
  + 该 token 路由的 8 个专家 ≈ 15 MiB
  ≈ 2415 MiB

MTP draft 每步：
  只读 8 个专家 ≈ 15 MiB（MTP 层只有 1 层，没有那 2326 MiB 的非专家大头）

draft 占主模型一步的比例 = 15 / 2415 ≈ 0.6%
```

**即使把 draft 的所有读取提速 8 倍（DDR 25 GB/s → GDDR6 200 GB/s），总时间也只省 0.5%。** 这与实测的 0.7%（噪声内）完全吻合。

### 更深一层的洞察：MoE 的批量验证几乎不摊薄权重读取

dense 模型做投机解码，验证 γ+1 个 token 只读一次权重 → 接近 (γ+1)× 加速。
但 **MoE 的每个 token 路由到不同的专家**，验证 6 个 token 要读最多 48 个专家（89 MB）而不是 8 个（15 MB）——**专家读取接近线性增长**。

这解释了三个实测现象：
1. MTP 只带来 +25%（而非 dense 的 2-3×）
2. nmax=3 与 5 无显著差异（第 4-5 位接受率仅 5-18%，多读的专家不划算）
3. **优化 draft 本身（搬 GPU）没有意义**——瓶颈在"主模型要读多少专家"，不在"draft 快不快"

## 四、那 MTP 的 +25% 到底从哪来

不是"draft 便宜"，而是**主模型少跑了步**：
- 无 MTP：每产 1 token 要走一次主模型（2415 MiB 读取）
- 有 MTP（nmax=5, E≈2.8）：每步主模型验证一批，产出 2.8 token，但只付一次"非专家 2326 MiB"的读取
- **省的是那 2326 MiB 非专家权重的重复读取**，这部分才是真正被摊薄的

所以优化方向应该是"让每步验证更多有效 token"（提高接受率），而不是"让 draft 更快"。而接受率受限于只有 1 个 MTP 头、自回归误差累积——**这是训练问题，不是配置问题**。

## 五、如果一定要省显存，更划算的做法

| 方案 | 省 | 代价 | 评价 |
|---|---:|---|---|
| ctx 96K→60K | 292 MiB | 压缩提前到 33K，可用上下文少 30K | 与 MTP 无关，但确实能省 |
| MoE cache 1350→1000 | 350 MiB | 命中率略降（主模型会变慢） | 直接掉速，不划算 |
| 禁用视觉 | 858 MiB | 失去多模态 | 用户已明确要保留 |
| 降 ctx 到 60K + 砍 cache 到 1050 | 642 MiB | 双重代价 | 换来 0.7% 速度，完全不值 |

## 六、短答

**不能，或者说没意义。**
1. **60K 不够**：省 292 MiB 后余 192 MiB，低于安全线（450），接近必卡阈值（186）
2. **搬上去也没收益**：实测 +0.7%（噪声内）；理论上限 0.6%——因为 draft 只占总读取的 0.6%
3. **根本原因**：MoE 的批量验证不摊薄专家读取，MTP 的价值在"省非专家权重的重复读取"，不在"draft 快"
4. **要真正突破，只有重训多头 MTP / 换 EAGLE3 侧车**，那是训练任务

**建议：维持现状（96K ctx + MTP 在 CPU + nmax=5）。** 这已经是这套硬件上"不重训"条件下接近最优的组合。
