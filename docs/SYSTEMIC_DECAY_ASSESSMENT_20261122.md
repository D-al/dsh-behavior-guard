# 系统性腐化评估与第一性原理管理（2026-11-22）

> 用户问："整个项目体系是否已庞大到可能出现系统性腐化的程度？从第一性原理怎么管理？
> 遇到了什么经典问题？最优解法？"
> 两路并行调研（腐化理论/度量 + 复杂度管理第一性原理）+ 本地实测。

## 一、最准确的命名（两个经典问题叠加）

**问题 1：架构腐化 (architectural erosion / design drift)** —— Perry & Wolf 1992 定义：
实现偏离预设架构与设计决策的累积漂移。Lehman 第二定律："随着系统演化，复杂度增加，
除非做工作来保持或降低它"。

**问题 2（更精确针对我们的模式）：Cargo-cult 稳定性剧场 + 负反馈 degraded**
每次事故加一层防护 → 防护本身成为成本中心，但**不产生新信息**。
安全工程称 "security theater"（看起来安全但不增实际安全）；
软件侧对应 "defense in depth 的边际递减" + Brooks 的 accidental complexity 累积。

** deepest：这是"控制回路饱和"**——控制机制数量增长快于被控系统的真实风险增长，
每层新增审计只在审计前一层审计，形成递归空转（我们已画过 5 层递归链）。

## 三、腐化判据实测（关键结论：腐化前夜，尚未确诊）

### 🔴 判据1：Ratchet（只增不减）— 阳性
- 4 天文件数 42 → **210**（5 倍），11-22 仍 +24
- 净删除行数占比 **10.3%**（健康 20-40%）
- 删除记录几乎为零 → 典型 ratchet，无退役机制
- Lehman：不主动做减法，复杂度必然单调增

### 🔴 判据2：复杂度集中 — 阳性
- index.mjs top 20% 函数占 **71%** 代码
- `guardDecide` **736 行**、`stateOf` 458 行 —— 上帝函数
- 热点集中 = 修改一处坏三处的高风险区

### 🔴 判据3：稳定性剧场（只检测不拦截）— 强阳性
真实 trace 1656 行（排 s1）：
- injection_hit **234**（检查层活跃）
- control_turn **7**、review_verdict 8、crit_hit 4
- **检查层:决策层 ≈ 33:1**
- 但关键在于：所有 injection 都是**软提示注入**——检查发现了问题，
  多数没有硬阻断（除 D4/D5 少数），大部分是"记一笔"
- 60 项门禁在真实会话中触发的只有少数几类事件 → 大部分门禁是"注册了但没实战"

### 🟡 判据4：文档-代码脱节 — 部分阳性
- 96 份文档 / 934K，但已发现设计文档写了代码零实现（CONSISTENCY_GUARD）
- 文档数量本身不是问题，**文档与代码的比例和同步成本**是问题

### 🟡 判据5：机制有效性 — 已抓到 6 张虚报 + 1 处判据体检
- 7 张 done 卡判据不过（已修 6，剩 M5 manual）
- 判据体检器第一版误报 15 处（backlog 卡）→ 状态过滤后 0
- 说明：体系已有自检能力（这是好消息），但腐化确实在发生

**综合判读：符合"腐化前夜"特征——ratchet + 热点 + 剧场三项阳性。
但尚未"确诊腐化"（功能仍可运行、自检机制还在工作）。这是最佳干预窗口。**

## 四、经典理论与成熟度

| 理论 | 核心 | 我们场景 |
|---|---|---|
| Lehman 演化定律 | 复杂度单调增，除非主动维护 | ✅ 解释 ratchet |
| Brooks 本质/附属复杂度 | 附属复杂度不解决本质困难 | ✅ 检查层是附属，决策质量是本质 |
| Architecture erosion (Perry & Wolf) | 实现偏离设计决策的漂移 | ✅ 设计≠代码反复出现 |
| Security theater | 看似防护但不增安全 | ✅ injection 软提示多为剧场 |
| Cargo cult engineering | 复制形式不理解本质 | ⚠ 部分门禁注册但无实战 |
| Gall's law | 复杂系统从简单演化而来 | 我们是从简单长出来的，符合；但需防过度分化 |
| Ashby 必要多样性 | 控制器复杂度需匹配环境 | ⚠ 控制复杂度已超环境真实风险 |
| Dijkstra "simplicity is prerequisite for reliability" | 简单是可靠的前提 | ✅ 最优解方向 |

## 五、最优解（第一性原理）

### 核心洞察
**这不是"加更多检查"的问题，是"负反馈回路失衡"的问题。**
系统有大量正反馈（每次事故→加检查→更多复杂度→更多事故面），
但缺少负反馈（定期减法、机制退役、有效性证伪）。

### 最优策略：从"增长型治理"转"稳态型治理"

**1. 建立减法机制（ratchet 反转）**
- 每次新增一个机制，必须同时评估一个旧机制的退役（one-in-one-out）
- 设"复杂度预算"：工具数/文档数/门禁数设上限，超了必须先删后加
- 规则/检查加 `retire_when` 元数据（已在 rulepack 部分实现）

**2. 区分剧场与真防护（有效性证伪）**
- 对每个检查问："它在真实会话中拦过什么？"——没有实战记录的降级为 warn 或删
- 用 mutation testing 思路：故意注入已知缺陷，看检查是否报警（我们已对 sentinel 做过）
- 不接受"注册了就算防护"

**3. 拆分上帝函数（热点治理）**
- `guardDecide` 736 行按机制拆成小函数 + 单测（参考 S17 函数外置模式）
- 这不是为了好看，是为了让下一次改动可归因

**4. 决策环优先于检查环（接上一轮 TOC）**
- 继续加检查边际收益≈0（Amdahl）
- 把资源转向 Orient + 元决策 + 写回 + 常驻闭环

**5. 冻结新增，验证有效后再加**
- 新机制先进 staging，观察它在真实会话中是否有实战价值
- 有价值的转正，无价值的自动退役——把"末位淘汰"引入机制生态

### 一句话
**系统还没烂，但正在按"只增不减 + 控制过度 + 剧场化"的路径走向腐化。
最优解不是再加一层治理，而是给治理体系本身加负反馈：复杂度预算 + 一进一出 + 有效性证伪。**
