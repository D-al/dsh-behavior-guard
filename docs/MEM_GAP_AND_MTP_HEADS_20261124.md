# 访存效率缺口是什么 + MTP 能否加头（2026-11-24 凌晨）

> 用户两问：① 访存效率缺口是什么？② 怎么给 MTP 加头？

---

# 一、访存效率缺口是什么

## 1.1 先把"缺口"量化出来（全部本机实测）

| 测量项 | 方法 | 结果 |
|---|---|---:|
| 硬件 STREAM 带宽（读+写）| numpy 大数组 copy，7 次中位 | **25.4 ~ 33.6 GB/s** |
| 单线程纯 memcpy | ctypes msvcrt.memcpy 256MiB | 8 ~ 14 GB/s |
| **decode 实际有效带宽** | 23 t/s × 0.608 GB/token | **14.0 GB/s** |
| DDR4-3200 双通道理论 | — | 51.2 GB/s |

**缺口 = 25.4 / 14.0 ≈ 1.8×**（保守取 STREAM 低值）。这就是"理论上限 41.8 t/s vs 当前 23 t/s"那个 1.82× 的物理来源。

## 1.2 关键实测：**不是访问模式的问题**

我原本以为 MoE 随机读 1.8MB 块会比顺序读慢很多。实测直接推翻：

```
专家池 2048 MiB，64 × 1.8MiB 块
顺序读: 11.0 GB/s
随机读: 10.8 GB/s
随机/顺序 = 0.99   ← 几乎完全一样
```

**原因**：1.8MB 的单块已经远大于预取器的有效视窗，顺序和随机对 DDR 来说都是"一大段流式"。所以"专家分散在 19GB 里导致随机访问"这个猜测**不成立**。

（注：sum 只有 11 GB/s 是因为 numpy 的 sum 有计算开销，不能当纯读带宽；纯拷贝能到 25-33。这里只用它做**相对比较**，相对结论有效。）

## 1.3 缺口的真正来源：**解包 ALU 堵住了内存流水线**

Q4_K 的 dot 不是"读一个数乘一个数"，每个 32 权重的 block 要做：
```c
memcpy(utmp, x[i].scales, 12);          // 复制 12 字节 scale
// 4 行位运算重组 6bit scale + 6bit min
_mm256_cvtepu8_epi16(...);              // 类型转换
4×2 次 _mm256_maddubs_epi16(...);       // 真正的 dot
```
**解包指令数 ≈ dot 指令数**——一半的 ALU 时间花在"把量化格式翻译成能算的数"上。

这完美解释了所有实测现象：
- **CPU 590% 占用但 ALU 利用率只 7-10%**：线程在等内存（stall），不是在算
- **但把专家并行（治延迟）反而慢 3-5%**：因为并行化后每个专家只剩 1 个线程算，行级并行度从 8 降到 1，解包+dot 的单线程吞吐本来就不够，延迟是藏住了但总时间更长
- **预取无效（t=0.59）**：数据预取来了，但解包 ALU 跟不上，数据在 L2 里等
- **tiled 慢 60%**：分块带来的额外索引/控制流开销，加在本已紧张的 ALU 上

**一句话**：缺口不是"带宽没打满"，也不是"随机访问慢"，而是**"解包计算与内存读取无法重叠"**——ALU 忙的时候，内存控制器在空转；内存喂数的时候，ALU 在等。两者串行，各占一半时间，所以利用率只有一半。

## 1.4 为什么难补（本轮已试遍）

要补这个缺口，必须让"解包 block N"和"预读 block N+1"重叠（软件流水线）。但：
- ggml 的 `ggml_vec_dot_q4_K_q8_K` 是紧循环，改成软件流水线要动 kernel 核心，且会打乱 MoE cache 的 buffer 布局
- 预展开 scale 表能省解包指令，但 scale 从 12 字节涨到 16 字节（+2.8% 带宽），在带宽紧张时净负
- 换 IQ 系列量化（查表解码）在无 AVX512 的 AVX2 上更慢（社区实测 IQ2_XS 70.3 vs Q2_0 93.8 t/s）

**结论**：这是当前硬件（AVX2 无 VNNI）+ 当前 kernel 结构（解包与 dot 串行）的**结构性上限**，不是某个开关能打开的。

# 二、MTP 能不能加头

## 2.1 直接结论：**不能加，但"加头"的功能已经存在**

### 模型层面：加头不可行
- GGUF 元数据 `qwen35moe.nextn_predict_layers = 1`——模型训练时只有 1 个 MTP 头
- 这不是小 LM head，而是**一个完整的 Transformer 块**：n_embd=2048、ffn=6144、attn + 2 个 norm + eh_proj + shared_head_norm，**0.84B 参数 ≈ 0.5 GB**
- 源码 `src/models/qwen35moe.cpp:~524` 有硬性 `GGML_ASSERT(n_layer_nextn == 1)`——**多传一个 MTP 层会直接 assert 崩溃**
- 要真加头 = 训练新头权重（需要训练流程 + 数据），不是配置能解决的

### 引擎层面："加头"的等价物 = `--spec-draft-n-max`
MTP 的 draft 是**自回归**的（源码 `common/speculative.cpp:~2113` 的 `while (n_drafting > 0)` 循环）：
```
用 1 个 MTP 头预测 token[1] → 把 token[1] 喂回去 → 预测 token[2] → ... 共 n_max 次
```
所以 `--spec-draft-n-max 6` 已经在做"同一个头连猜 6 个"。**加头的效果，调 n_max 就能得到**，不需要新头。

## 2.2 当前 n_max 已过最优，甚至偏大

从日志实测（1608 条 `draft acceptance` 记录）：
```
draft acceptance = 0.91892 (204 accepted / 222 generated), mean len = 3.24
draft acceptance = 0.91304 (126 accepted / 138 generated), mean len = 3.47
```
**acceptance 92%，但 mean len 只有 3.24**。

如果每位置都是 0.92，n_max=6 的理论期望接受长度 = `(1-0.92^7)/(1-0.92) = 5.5`。实测只有 3.24 → **说明第 3-4 位之后接受率暴跌**，后面 2-3 个 draft token 基本是白猜（多付验证成本、几乎不被接受）。

这与之前实测 `nmax=7 更慢（26.73 < 27.31）` 完全一致——**n_max 的收益在 4-5 附近就到顶了**。

### 可做的微调（收益小）
- `n_max 6 → 4~5`：少 draft 2 个白费的 token，理论上省一点验证开销
- 但收益估计 <5%，而本机 sd≈4 t/s，**测不出来**。要测准必须看 `acc per pos`（需要 `-lv 4`）

## 2.3 顺手发现的两个配置缺陷

### (a) ngram 那三个参数当前**完全无效**
autostart 传了：
```
--spec-ngram-simple-size-n 12 --spec-ngram-simple-size-m 32 --spec-ngram-simple-min-hits 2
```
但 `--spec-type` 只写了 `draft-mtp`（单个值）。**没有列出 ngram 类型，这几个参数就不会启用 ngram 投机**。

### (b) `--spec-ngram-simple-min-hits` 本身是 no-op
源码 `common/speculative.cpp` 里 `min_hits` 只出现 6 次：3 次打印日志，第 6 次在 `common_ngram_map()` 里——那是 **ngram_map_k** 类型，不是 ngram_simple。**对 ngram-simple 类型完全没用到**。

所以 autostart 注释里写的"至少命中 2 次才提议，提高接受率"**从来没有生效过**。

### (c) size_m=32 与 n_max=6 不匹配（如果真启用 ngram）
ngram_simple 的 `size_m` 是"每次起草长度"，`n_max` 是"最大验证 token"。如果 size_m=32 生效，会起草 32 个 token，而 n_max=6 只验证 7 个——**大部分 draft 白做**。注释说"默认48，收保守些"改成 32，仍然远超 n_max。

## 2.4 真正值得做的两件事

| 动作 | 收益 | 成本 |
|---|---|---|
| **1. 加 `-lv 4` 看 `acc per pos`** | 精确定位 n_max 拐点（是 3 还是 5） | 改日志级别+重启，零风险 |
| **2. 清理无效的 ngram 参数** | 无性能收益，但消除"以为它生效"的误解 | 改 autostart，低风险 |
| 3. n_max 调 4 或 5 试 | <5%，测不准 | 低 |
| 4. 真启用 ngram 投机（改 spec-type） | **不确定**：对代码重复多的场景可能有用，对自然语言通常没用 | 需 A/B，且与本机 agent 场景匹配度未知 |

## 2.5 诚实总结

- **"加头"在模型层面不可行**（1 个头是硬约束，源码 assert 锁死，加头=重训）
- **但功能上不需要加头**：`n_max` 已实现"同一个头连猜 N 个"，且当前 n_max=6 已经超过实测最优点（mean len 只 3.24）
- **想提升投机收益，唯一有意义的动作是用 `-lv 4` 看 `acc per pos` 找到真实拐点**，而不是盲目加 n_max 或加头
- 顺带发现 autostart 里 3 个 ngram 参数**全部无效**（spec-type 没启用 + min-hits 是 no-op + size_m 不匹配），是一处配置噪声

# 三、两个问题的短答

**访存效率缺口是什么？**
是"Q4_K 解包计算和内存读取串行"造成的 1.8× 损失——硬件能到 25 GB/s，实际只用到 14 GB/s。实测排除了"随机访问慢"（随机/顺序=0.99）和"带宽打满"（只 55%）。要补需要改 dot kernel 做软件流水线，本轮所有轻量尝试（专家并行/预取/tiled）都失败，因为都会牺牲行级 ALU 并行度。

**怎么给 MTP 加头？**
加不了——模型只有 1 个 MTP 头（0.84B 参数的完整 Transformer 块），源码硬 assert 锁死。但"加头"的效果已经通过 `--spec-draft-n-max`（自回归连猜 N 个）实现，当前 6 已偏大（实测 mean len 只 3.24，后面 2-3 个是白猜）。真正该做的是 `-lv 4` 看逐位置接受率找拐点，而不是加头。
