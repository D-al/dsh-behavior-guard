# 路线图是否拆成多文件？三维度分析（2026-11-20）

> 用户问："有没有必要把路线图拆分成多个文件？从有效性、可维护性、高容错性分析。"
> 方法：主代理核查 + 独立 Explore 审计（影响面盘点）交叉验证。
> 结论：**值得做"一刀切"的最小拆分，不值得做三层全拆**。详见 §4。

## 0. 现状底数（证据）

| 指标 | 实测 |
|---|---|
| ROADMAP.md 总行数 | 973 |
| 人读导航 §1-§6 | 182 行 |
| 归档+证伪 §7-§8 | 51 行 |
| 机器权威块（附录 A）| **727 行（75%）** |
| what/why 逐字重复 | **32/32**（机器块 vs CAPABILITY_LADDER.yaml）|
| 状态副本 | 4 处（机器块 / LADDER 镜像 / HUMAN 表 / 生产 cp）|
| test_sids 副本 | 3 处（ROADMAP 顶层+meta / LADDER meta / test_sids.json）|
| README 锚点链接 | 5 个（全部指向 §1-§8，不指向附录）|

## 1. 有效性（能否让人与 agent 各自高效拿到正确信息）

**收益：中等偏正。**
- 拆后 `ROADMAP.md` 从 973 行 → ~245 行，人打开即见导航；agent 读 `ROADMAP_GRAPH.md` 得到纯净 YAML，不必从 Markdown 里正则抠块。
- **但收益上限有限**：上一轮已把机器块移到文末附录，人的"30 秒读懂"已经不再被 YAML 挡住（§1 在第 14 行）。拆分是锦上添花，不是救命。
- **关键反证**：`--next/--card/--dry-run` 的输出今天已经正确（M8、8147 数字统一、evidence_cited 判据真实跑通）——说明当前架构**在功能上是有效的**。拆分的动机不是"现在不好用"，而是"长期更干净"。

## 2. 可维护性（改一处要动几处）

**收益：最大——这是拆分的真正理由。**
- **死副本可一次消除**：机器块里 23 项 × what/why/caveats 等字段与 LADDER 逐字重复，而 `roadmap_check.py:45-54` 运行时本来就用 LADDER 覆盖块内同名字段——**块内语义是永不被读的死副本**。拆分时只留 status/verify/deps/evidence_log 在机器层，语义只在 LADDER，可净删 200-300 行且零行为变化（`growth_card()` 读的是合并结果）。
- **写回路径变清晰**：现在 `save_authoritative()` 一次 write 同时改 Markdown 正文和机器块；拆后分成"写机器文件 + 写人读表"两次 write，各自职责单一。
- **但必须付的账**：4 个文件要同步改——`roadmap_check.py:25,38,249,275`（路径）+ `:209,342`（文案）+ `package.json:12`（tarball files）+ `GUARD_MANIFEST.yaml:14`（key_files）+ `setup/sync-to-profile.ps1:17`（生产同步）。漏一个就会出现"本地对、生产错"。

## 3. 高容错性（出错概率 + 出错后能否被发现）

**收益：中性偏正，但有一个反直觉的风险。**

利：
- **写操作隔离**：今晚 A3_5 那次事故——agent 用 `write` 重写整个 `self_harness_gate.py`，把 11 项 self_test 缩成 2 项、改坏了 `accept()` 返回语义——根因就是"机器可写区域与人读区域在同一文件"。拆后 agent 的 `--apply` 只写机器文件，**物理上碰不到 §1-§8 的叙述**，这类误伤不会再发生。
- **误编辑面缩小**：人手工编辑 ROADMAP.md 时不可能再损坏 YAML 块（现在一个养行空格就让 `git diff --check` 拦住 apply，今晚真实发生过）。

弊（反直觉）：
- **文件数增加 ≠ 副本数减少**：生产同步仍需 cp 两个文件而非一个；一致性守卫的 `key_files` 也要多监控一项。拆分本身**不解决"权威→生产"这个最大的漂移源**（今晚 M1 埋点不生效就是我漏了这步）。
- **"同一句话两处维护"不会因拆分自动消失**：分析过程中我刚抓到自己上轮重绘的遗漏——ROADMAP.md 静态文案改成了"文末附录 A"，但 `roadmap_check.py:270` 的生成模板仍写"上方"，下次 `--apply` 就会把文案改回错误指向。**拆分后这句话仍会存在于两处（人读文件 + 生成模板）**，必须靠规范而非结构来防。

## 4. 结论与建议

### 值得做，但只做"最小一刀"

**新 `ROADMAP_GRAPH.md` 只放裸 YAML 块；`ROADMAP.md` 保留 §1-§8 + HUMAN_PROGRESS 表。**
- 5 个 README 锚点零断链（都指向 §1-§8）
- 14 处无锚点 ROADMAP.md 链接不受影响
- §7 归档和 §8 证伪清单**留在主文件**——用户明确要求"被证伪的方向记在活文档主入口"，拆到 archive 会让它难找

### 分两阶段，不要一次做完

**阶段 1（低风险、建议现在做）**：搬块 + 改 4 处引用 + 验收。约 727 行搬迁，行为零变化。
**阶段 2（可延后）**：消除 23×语义死副本 + test_sids 三份归一 + docs 历史措辞更新。收益大但不紧急，且阶段 1 稳定后再做更安全。

### 什么情况下不值得拆

如果这个项目近期不再新增自治卡（`--next` 已到 M8，剩余多为 manual-blocked），维护频率会大幅下降——那么拆分带来的长期收益也同步下降。**判断触发条件**：未来两周若继续每周爬 ≥1 张卡，值得拆；若进入人工决策期，维持现状即可。

## 5. 说明：本分析不改变任何文件状态

用户问的是"有没有必要"，本轮只做分析与证据核验。分析过程中修复了一个上轮重绘引入的文案回退 bug（`roadmap_check.py:270` 生成模板指向"上方"），此项属既有欠账修正，不属于拆分实施。
