# ADR-0022：KR4 时间盒阈值按实测重定 + 冷热会话分离

- 状态：accepted
- 日期：2026-11-22
- 决策者：用户（显式批准："按实测重定阈值（推荐）"，2026-11-22 14:44）
- 决策层级：重要决策 I（改变验收判据，有实测支撑）
- 支撑决策：ADR-0020（KR 体系落地）

## Context（背景）
KR4 声称测"预埋事件在时间盒内反应"，v3.1 写死 30s 时间盒（P1-6），**当时无实测依据**。
2026-11-22 用真实 dsh 会话测量（bridge 发消息 → 从 session events 提取 user/message.time → tool/call.time）：

| 场景 | 延迟 | 来源 |
|---|---|---|
| 会话1首请求（冷）| 90.5s | dsh-8 |
| 会话1第二请求（暖）| 25.8s | dsh-39 |
| M1首请求（新会话）| 40.8s | dsh-8 |
| M1第二请求（暖）| 6.6s | dsh-40 |

另有一次并发测量（3 实例）导致显存 7812/7958 MiB（余 145 MiB，逼近换页红线），
延迟数据被资源竞争污染，**已作废、不作阈值依据**。

## Options
| 方案 | 做法 | 结论 |
|---|---|---|
| A 维持 30s 不分开 | 冷热混判，首请求必 FAIL | ❌ 把环境 prefill 成本当成 agent 能力缺陷 |
| B 按实测分离冷热（选中）| 暖态≤30s，冷启动标注不计入 | ✅ 阈值有据、测的是 agent 响应能力 |
| C 去掉时间盒 | 只测有动作+证据 | ❌ 退回构念弱化（不测及时性）|

## Decision
1. KR4 时间盒**保持 30s**，但**仅适用于暖态会话**（同一会话第 2 次及以后的外部事件）。
   实测暖态 6.6s / 25.8s 均在 30s 内 → 阈值有据，不是拍脑袋。
2. **冷启动/首请求不计入 KR4**：首轮含 90K context 的 prefill（40.8~90.5s），
   属测量环境特性，不是 agent 的感知-反应能力。提取器标注 `cold=true` 并排除。
3. **harness 内部消息不算外部事件**：`[harness *]` 前缀 / 非 `source.kind=user` 的消息
   是系统反馈环，不得刷 KR4 数据（已修 tools/kr4_from_dsh.py）。
4. **并发测量作废**：单 GPU 8G，多实例并发抢显存污染延迟；KR4 测量必须串行。

## Counter-evidence（反证）
- **反对**：4 个数据点（2 冷 2 暖）样本太小，暖态 25.8s 已逼近 30s，若再测出现 >30s 则阈值仍偏紧。
- **翻案条件**：若累计 ≥10 次暖态测量中 >20% 超 30s，则上调时间盒并重开 ADR。
- **独立性**：4 点来自 2 个会话，同源风险；冷/暖分离的物理依据（prefill vs 驻留）独立于样本。

## Consequences
- 正面：KR4 阈值有实测依据、构念正确（排除冷启动与内部消息）。
- 负面：CR4 有效样本需暖态会话，测量成本略增（首条预热不计）。
- 验证：kr4_from_dsh.py 提取仅含外部用户事件；暖态延迟 ≤30s 才 PASS。
